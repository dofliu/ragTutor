第 035 堂進階約 15 分鐘

Doc2Query 文件擴展：建索引時先替每段預測「別人會怎麼問」

技師問「葉片轉不動」，手冊寫的是「煞車線圈電阻、釋放間隙」，字面沒有一個詞重疊，關鍵字檢索就找不到。Doc2Query（Document Expansion by Query Prediction）換個方向解決：不改查詢，而是在建索引時先用模型替每個段落預測「會有人用什麼問題來找這段」，把預測的查詢附加在段落後面再建索引。口語說法就預先接上了手冊的用詞。

🎬 動畫：把「別人的說法」預先放進索引

🧩 重點整理

文件端擴展查詢改寫、HyDE 是在查詢端補字；Doc2Query 是在文件端補字：離線為每段預測可能的查詢，附加後再建 BM25 或其他索引。
查詢階段不變生成只在建索引時做一次，查詢時照舊檢索，不多一次模型呼叫。代價是索引變大，且段落更新時要重新生成。
幻覺查詢生成模型會寫出段落裡沒有的內容，這些查詢進了索引就會把不相關的段落拉進結果。Doc2Query-- 用相關性模型替預測查詢打分，只保留高分的。
適用情境詞彙落差大（口語對手冊用詞）、文件相對穩定、查詢量大的場景。與重排序、SPLADE、混合檢索可以並用。

🧪 互動範例：有無文件擴展，以及過濾門檻

知識庫是 10 段虛構的《OW-8 運維手冊》段落。每段有幾句預先寫好的預測查詢（模擬生成模型的輸出，並附一個模擬的相關性分數；真實系統由模型生成與打分），其中 PT-205 煞車段帶有一句幻覺查詢。檢索是瀏覽器內真的在算（BM25，中文用二字詞）。請比較「只用原段落」與「附加預測查詢」，並拉動過濾門檻，看分數低的預測查詢被濾掉後結果的變化。

過濾門檻（預測查詢分數低於此值就丟掉）：
A. 只用原段落建索引
B. 原段落＋預測查詢（過濾後）建索引

💻 程式範例（Python）

下面是文件擴展的最小實作：用 claude-sonnet-5 為每段生成預測查詢，附加後用 rank_bm25 建索引。重點在離線的「生成 → 附加 → 建索引」。範例以空白斷詞，中文實務上請換成適合的斷詞器；Doc2Query-- 的過濾需要另一個相關性模型（例如 cross-encoder），這裡只示意介面。

import anthropic
from rank_bm25 import BM25Okapi

client = anthropic.Anthropic()

DOCS = [
    "PT-205 旋角馬達煞車異常：量測煞車線圈電阻，檢查釋放間隙與煞車片磨耗。",
    "PT-203 旋角馬達過溫：檢查冷卻風扇與散熱片積塵，確認負載電流。",
    "進入輪轂前須先順槳、鎖定葉輪並執行上鎖掛牌（LOTO）。",
]

def predict_queries(doc, n=3):
    prompt = (f"請寫出 {n} 個現場技師會用來查這段手冊的口語問題，每行一個，"
              f"只能根據段落內容，不要加入段落沒有的資訊。\n\n段落：{doc}")
    msg = client.messages.create(model="claude-sonnet-5", max_tokens=200,
                                 messages=[{"role": "user", "content": prompt}])
    return [q.strip() for q in msg.content[0].text.splitlines() if q.strip()]

def keep_relevant(doc, queries, scorer, threshold=0.5):
    # Doc2Query--：scorer(query, doc) 回傳相關性分數，低分的預測查詢丟掉
    return [q for q in queries if scorer(q, doc) >= threshold]

# 離線：生成、過濾、附加、建索引（score 為你的相關性模型）
expanded = []
for d in DOCS:
    qs = predict_queries(d)
    # qs = keep_relevant(d, qs, scorer=score)
    expanded.append(d + " " + " ".join(qs))
bm25 = BM25Okapi([e.split() for e in expanded])

# 線上：查詢照舊，不多一次模型呼叫
scores = bm25.get_scores("葉片轉不動".split())
print(DOCS[int(scores.argmax())])

實務上要記得：回傳給使用者與模型的仍是原段落，預測查詢只用來建索引；另外要記錄每段的生成版本，段落更新時一併重生。

⚠️ Doc2Query 常見的坑 / 何時不該用

  • 幻覺查詢：模型寫出段落沒有的內容（如 PT-205 段被預測「PT-203 過溫」），會把不相關段落拉進結果。提示要限制「只能根據段落」，並用相關性模型過濾（Doc2Query--）。
  • 告警代碼被稀釋：預測查詢太多，會讓精確比對的代碼、料號與其他詞混在一起。數量不要多，並檢查代碼類查詢有沒有變差。
  • 文件常更新：每次修改段落都要重新生成預測查詢，生成成本與版本管理要算進去。
  • 索引變大：每段多出的詞會增加索引大小，數字要用自己的資料量測，不要照搬別人的倍數。
  • 回傳錯東西：預測查詢只用來建索引，不要把它們混進給模型的上下文，否則答案可能引用到不存在的內容。
  • 語意檢索已夠好時：若向量檢索已能處理口語問法，增益可能有限；先用評估集（第 021 堂）比較再決定。
風場、機型、手冊內容、告警代碼與預測查詢皆為虛構，實際作業以原廠手冊與現場規範為準。互動範例的預測查詢與分數是預寫腳本，不是真實的模型輸出。

延伸閱讀：Nogueira、Yang、Lin 與 Cho，Document Expansion by Query Prediction（2019）；Gospodinov、MacAvaney 與 Macdonald，Doc2Query--: When Less is More（ECIR 2023）。

📝 小測驗

Doc2Query 在哪個階段呼叫生成模型？

Doc2Query 是離線的文件端擴展，查詢階段不需要多呼叫模型，代價是索引變大與更新要重新生成。

Doc2Query-- 為什麼要用相關性模型替預測查詢打分？

生成模型會寫出段落沒有的內容；這些查詢進索引會把不相關的段落拉進結果，所以先打分再過濾。
