第 039 堂進階約 14 分鐘

問題分解：一句話問了好幾件事，就先拆開再查

技師一句話問：「PT-203 與 PT-205 同時出現，各先檢查什麼？煞車線圈備品還有嗎？」整句變成一個查詢，名額被某個需求佔滿，另一個需求常被擠掉。問題分解（Query Decomposition）先請模型把複合問題拆成一次只問一件事的子問題，各自檢索，再合併證據回答。

🎬 動畫：先拆開，再各查各的

🧩 重點整理

複合問題 = 多個需求一句話含好幾件事時，整句只會變成一個向量，每個需求只分到一部分相似度，名額容易被其中一個佔滿。
拆成獨立子問題請模型拆成一次只問一件事的子問題，並保留告警代碼等關鍵識別詞；每個子問題單獨檢索，可同時送出。
合併前要去重各路結果合併成上下文，重複的段落只留一份，再讓模型依據證據回答。每路也可用不同的資料源。
相依就要依序後一題用到前一題答案時，不能同時送出，要一題一題來（見第 034 堂 IRCoT）。拆錯、漏拆會一路傳到答案。

🧪 互動範例：整句檢索 vs 問題分解

知識庫是 8 條虛構的《OW-8 運維手冊》與備品表句子，檢索是瀏覽器內真的在算（BM25，中文用二字詞）。問題要三件事：PT-203 先檢查什麼、PT-205 先檢查什麼、煞車線圈備品。三個子問題是預先寫好的示意（真實系統由模型產生）；你可以切換「分解的好壞」，並調整名額，比較兩種做法找到幾項必要事實、帶進幾段無關內容。

💻 程式範例（Python）

下面是最小實作：用 claude-sonnet-5 把問題拆成 JSON 陣列的子問題，子問題各自用 BM25 檢索（可平行），合併去重後再回答。範例以空白斷詞，中文實務上請換成適合的斷詞器；分解結果要檢查，且要限制子問題數量。

import json
import anthropic
from concurrent.futures import ThreadPoolExecutor
from rank_bm25 import BM25Okapi

client = anthropic.Anthropic()
MODEL = "claude-sonnet-5"
DOCS = [
    "PT-203 旋角馬達過溫時，先檢查冷卻風扇與散熱片是否積塵。",
    "PT-205 旋角馬達煞車異常時，先量測煞車線圈電阻與釋放間隙。",
    "煞車線圈備品料號 PT-BRK-01，基地二號庫目前庫存 2 組。",
]
bm25 = BM25Okapi([d.split() for d in DOCS])

def ask(prompt, max_tokens=500):
    msg = client.messages.create(model=MODEL, max_tokens=max_tokens,
                                 messages=[{"role": "user", "content": prompt}])
    return msg.content[0].text

def decompose(question, max_sub=4):
    out = ask("把問題拆成互相獨立的子問題，每題只問一件事，保留告警代碼等關鍵詞，"
              f"最多 {max_sub} 題，只輸出 JSON 字串陣列。\n問題：" + question)
    subs = json.loads(out)
    return subs[:max_sub] or [question]      # 拆不出來就退回整句

def retrieve(q, k=1):
    scores = bm25.get_scores(q.split())
    best = sorted(range(len(DOCS)), key=lambda i: -scores[i])[:k]
    return best

def answer(question):
    subs = decompose(question)
    with ThreadPoolExecutor() as pool:                # 子問題互相獨立，可同時檢索
        results = list(pool.map(retrieve, subs))
    ids = sorted({i for r in results for i in r})     # 合併並去重
    context = "\n".join(DOCS[i] for i in ids)
    return ask("只依據下列資料回答，資料沒有就說沒有。\n資料：\n" + context + "\n問題：" + question)

print(answer("WTG-17 的 PT-203 過溫、PT-205 煞車異常：各先檢查什麼？煞車線圈備品還有嗎？"))

實務上要把「子問題清單」與每路命中的段落一起記錄下來，才看得出是分解拆得不好，還是檢索沒撈到；並用評估集（第 021 堂）比較整句檢索與分解後的召回與延遲。

⚖️ 與前面課程的比較

多重查詢（第 006 堂）Step-Back（第 036 堂）IRCoT（第 034 堂）問題分解
要解決同一個需求有多種說法問題太具體，缺上位原則後一步要用前一步的結果一句話含多個獨立需求
做法改寫成多個同義查詢多問一個較抽象的問題推理與檢索交錯拆成子問題各自檢索
檢索次數多路，同一需求兩路多輪，依序每個子問題一路，可平行
額外成本一次改寫一次後退多輪生成一次分解，多路檢索
主要風險改寫偏離原意上位問題太籠統推理走偏拆錯、漏拆、丟失關鍵詞

⚠️ 問題分解常見的坑 / 何時不該用

  • 漏拆：模型少拆一個需求，那個需求就沒人查。可請模型在最後檢查「原問題的每個部分是否都有對應子問題」。
  • 丟失關鍵詞：子問題寫成「它先檢查什麼？」，告警代碼不見了，檢索會撈到錯的段落（互動範例可以試）。要求每個子問題都自成一句、保留識別詞。
  • 過度拆解：單一事實問題拆成好幾題，只是徒增延遲與雜訊。設定子問題數量上限，簡單問題直接檢索。
  • 相依的子問題：後一題要用前一題答案時，同時送出會失敗，要依序執行，或改用 IRCoT（第 034 堂）。
  • 合併時重複：不同子問題撈到同一段，要去重；也要控制合併後的總長度（第 031 堂的排序問題仍然存在）。
  • 安全相關步驟：拆解與回答仍要附出處（第 025 堂），涉及門檻值與作業安全的結論由人覆核。
風場、機型、手冊內容、告警代碼、工單、料號與庫存數據皆為虛構，實際作業以原廠手冊與現場規範為準。互動範例的子問題是預先寫好的示意，不是真實的模型輸出。

延伸閱讀：Press 等人，Measuring and Narrowing the Compositionality Gap in Language Models（Self-Ask，arXiv 2210.03350）；Zhou 等人，Least-to-Most Prompting Enables Complex Reasoning in Large Language Models（arXiv 2205.10625）。

📝 小測驗

問題分解最適合處理哪一種問題？

複合問題整句檢索時需求會互搶名額；拆成子問題各自檢索，每個需求都有自己的證據。

子問題 2 要用到子問題 1 的答案才能提問，應該怎麼做？

相依的子問題無法平行；要依序執行，這就是第 034 堂 IRCoT 處理的多跳情境。
