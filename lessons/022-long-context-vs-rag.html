長上下文 vs RAG：何時該用哪個

模型的上下文視窗越來越大，有人會問：乾脆把整本《OW-8 運維手冊》丟進去，還需要 RAG 嗎？答案是「看情況」。資料小、問題需要通盤閱讀時，長上下文（Long Context）最單純；資料大、常更新、每次只查一小段時，RAG 更省、更好追溯。這堂課比較兩種做法的取捨，並介紹先 RAG、不足再全文的混合路由。

🎬 動畫：整本塞進去，還是只撈相關的？

🧩 重點整理

資料量先決定可不可行整份資料放不進視窗，長上下文就不是選項。放得進去時，還要再看查詢量與更新頻率；視窗大小依模型而異，請以所用模型的文件為準。
問題型態決定準不準單點查找（一個告警代碼）RAG 又快又準；全局、跨章節或要「全部列出」的問題，Top-k 容易漏，長上下文較穩。
長上下文不是無限好用研究顯示相關資訊落在長輸入中段時，表現常比在開頭或結尾差；也有研究指出，模型實際能有效利用的長度可能短於它宣稱的視窗。
混合路由兩邊都顧先用 RAG 取片段，讓模型判斷夠不夠；不夠才送全文。是否划算要用自己的評估集量，不要直接套別人的結論。

🧪 互動範例：改變資料量、視窗與方式，看輸入量與證據涵蓋

下面是一批虛構的《OW-8 運維手冊》與相關文件，每份標有虛構的 token 數（單位 K）。選一個問題，切換資料範圍、視窗大小與做法：「全文塞入」會依序把文件放進視窗，放不下的部分被截掉；「RAG」用 BM25 取回 Top-k 片段（每個片段假設約 0.5K tokens）。看每次查詢的輸入量與標準依據有沒有進到模型眼前。試試「旋角系統有哪些保養項目？」把 k 調小，再把資料範圍調大。這裡沒有真的呼叫模型，只比較「證據有沒有被放進去」。

💻 程式範例（Python）

一個最小的「混合路由」：先算全文的 token 數，放得進預算就直接長上下文；放不進去就先 RAG，並讓模型回報「依據不足」時才退回全文（Self-Route 的簡化版）。用 anthropic SDK（pip install anthropic）。章節內容為虛構；檢索用字元二連詞重疊代替，實務請換成第 003～004 堂的向量或混合檢索。

import anthropic

client = anthropic.Anthropic()
MODEL = "claude-sonnet-5"

# 虛構的《OW-8 運維手冊》章節（實務上是整本手冊切成的章節）
SECTIONS = {
    "PT-203": "PT-203 旋角馬達過溫：檢查冷卻風扇與濾網，量測繞組溫度，降溫後復歸。",
    "保養-潤滑": "旋角系統定期保養：馬達與減速機潤滑，補充指定潤滑脂並檢查漏油。",
    "保養-電源": "旋角系統定期保養：備援電源檢測，量測電容電壓並執行備援電源測試。",
    "保養-軸承": "旋角系統定期保養：旋角軸承與齒圈檢查，目視磨損並抽查螺栓扭力。",
}
FULL_TEXT = "\n\n".join(f"## {k}\n{v}" for k, v in SECTIONS.items())

# 1) 全文有多少 token？用官方的計數端點，不要自己用字數估
def count_tokens(text):
    r = client.messages.count_tokens(
        model=MODEL, messages=[{"role": "user", "content": text}])
    return r.input_tokens

# 2) 玩具檢索：字元二連詞重疊（請換成向量／混合檢索）
def grams(t):
    return {t[i:i+2] for i in range(len(t) - 1)}

def retrieve(question, k=2):
    q = grams(question)
    ranked = sorted(SECTIONS.items(), key=lambda kv: -len(q & grams(kv[1])))
    return "\n\n".join(f"## {k}\n{v}" for k, v in ranked[:k])

# 3) 回答：只依據提供的內容；不夠就明說，方便路由判斷
def answer(question, context):
    resp = client.messages.create(
        model=MODEL, max_tokens=600,
        messages=[{"role": "user", "content":
            f"手冊內容：\n{context}\n\n問題：{question}\n"
            "只根據手冊內容回答；若內容不足以完整回答，只輸出 INSUFFICIENT。"}])
    return resp.content[0].text.strip()

# 4) 混合路由
def route(question, budget=150_000):
    fits = count_tokens(FULL_TEXT) <= budget
    if fits and LOW_QUERY_VOLUME:               # 資料小、查詢量低：直接全文
        return answer(question, FULL_TEXT)
    out = answer(question, retrieve(question))   # 先 RAG
    if out != "INSUFFICIENT":
        return out
    return answer(question, FULL_TEXT) if fits else "手冊中找不到足夠依據。"

LOW_QUERY_VOLUME = False
print(route("旋角系統有哪些定期保養項目？"))

全文模式若查詢很頻繁，可把不變的手冊放在提示的前段並啟用提示快取（prompt caching），讓重複的輸入更省；細節請參考官方文件。模型回報「依據不足」的判斷也會出錯，上線前要用評估集檢查路由的誤判率。

⚖️ 與前面課程的比較

長上下文全文塞入基礎 RAG（第 001 堂）進階 RAG（第 005～012 堂）混合路由
做法整份資料放進提示切塊、嵌入、取回 Top-k重排序、查詢改寫、父子文件、壓縮等優化檢索品質先 RAG，依模型判斷決定是否改送全文
優點流程單純；全局問題不漏輸入量小；可附出處；資料量不受視窗限制檢索更準，雜訊更少兼顧成本與完整性
缺點每次輸入量大；放不進視窗就無解；中段資訊較易被忽略全局或分散的問題可能漏檢索元件多，要調參數與維護多一道判斷，判斷也會錯；系統更複雜
成本隨資料長度與查詢量增加低且穩定略高（多一次重排序或改寫）介於兩者，視分流比例而定
適合用在單本手冊、低查詢量、通盤閱讀大量資料的單點查找檢索品質是瓶頸時兩類問題並存的值班問答

⚠️ 長上下文 vs RAG 常見的坑 / 何時不該用

  • 只看視窗大小就下結論：「放得進去」不等於「用得好」。要在自己的資料上測，不要只相信視窗規格或別人的基準。
  • 忽略位置效應：把關鍵段落埋在長輸入中間，表現可能變差（Liu 等人）。若走全文，把最重要的指示與資料放在開頭或結尾，並實測。
  • 忽略查詢量：一次全文不貴，一天一千次就很可觀。成本要用「每次輸入量 × 查詢量」估，並評估提示快取是否適用。
  • RAG 漏檢索卻沒人發現：答案看起來完整，其實少一項。全局型問題要用評估集量召回（第 021 堂），必要時改走全文或第 016 堂的摘要樹。
  • 全文模式失去出處：整本都在上下文，模型不一定會指出答案來自哪一節。要出處就要求引用章節，並抽樣核對。
  • 把兩者當成二選一：很多系統用 RAG 處理單點查找，全局問題另開全文路線。路由規則要用資料驗證，別憑感覺。
  • 安全關鍵內容不能靠任一方式單獨把關：高處作業、上鎖掛牌的步驟必須完整，不能因為漏檢索或被截斷而遺漏，需要專家審查。
  • 視窗與價格會變：本課的 token 數、視窗與成本比例皆為示意；實際選型請看當下的模型規格與計價。
風場、機型、手冊內容與數據皆為虛構，實際作業以原廠手冊與現場規範為準。互動範例的 token 數、視窗大小與檢索結果皆為示意，不可作為實際維修或成本決策依據。

延伸閱讀：Liu 等，〈Lost in the Middle: How Language Models Use Long Contexts〉（arXiv:2307.03172）；Li 等，〈Retrieval Augmented Generation or Long-Context LLMs? A Comprehensive Study and Hybrid Approach〉（arXiv:2407.16833，比較兩者並提出 Self-Route）；Hsieh 等，〈RULER: What's the Real Context Size of Your Long-Context Language Models?〉（arXiv:2404.06654）；Anthropic，〈Introducing Contextual Retrieval〉（文中提到知識庫較小時可直接放進提示並搭配提示快取）。

📝 小測驗

只有一本約 55K tokens 的手冊，視窗放得下，查詢量很低，使用者常問「旋角系統有哪些保養項目」這類要整節列出的問題。最合理的起點是？

資料小、放得進視窗、查詢量低，且問題偏全局，直接全文最單純，也不會漏檢索。之後若資料變大或查詢量上升，再重新評估。

混合路由（先 RAG，不夠再全文）主要想解決什麼？

混合路由的目的是兼顧成本與完整性；模型判斷「依據不足」也可能出錯，所以仍要用評估集驗證路由。
