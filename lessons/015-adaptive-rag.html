Adaptive RAG：依問題難度選擇路線

不是每個問題都值得同樣的力氣。「旋角系統是做什麼的」不必翻手冊；「PT-203 怎麼處理」查一次手冊就夠；但「WTG-17 的 PT-203 為什麼一直復發」要跨手冊、工單與振動報告一步步查。固定流程不是浪費就是答不全。Adaptive RAG（自適應 RAG）先用一個複雜度分類器判斷問題難度，再分流到不檢索、單步檢索、多步檢索三條路線之一。

🎬 動畫：先判斷難度，再選路線

🧩 重點整理

三條路線Adaptive RAG（Jeong 等人，NAACL 2024）依問題複雜度在不檢索、單步檢索、多步（迭代）檢索之間切換，讓簡單題不浪費、複雜題不缺資料。
分類器是關鍵由一個較小的語言模型預測問題的複雜度標籤，再決定走哪一條路線；它的判斷比跑完整流程便宜得多。
標籤自動產生訓練標籤不靠人工逐題標註，而是依各策略實際答對與否，再配合資料集本身的特性（單跳或多跳）補標。
路由不是魔法分錯一次，複雜題只拿到殘缺答案，簡單題則多花成本。它省的是不必要的呼叫，不會讓檢索本身變準。

🧪 互動範例：固定流程 vs 自適應路線

下面用虛構文件（手冊、工單、CMS 報告）建一個索引。檢索是真的在瀏覽器裡算（簡化的 TF-IDF 餘弦相似度）；多步檢索會真的分輪查詢並合併結果。但分類器在這裡是「規則」模擬的（比對「為什麼、根因、復發」等詞），不是訓練出來的模型，所以你可以輸入自己的問題，看它怎麼分流，也很容易找到它判錯的例子。「必要資料」是人工為三個範例題標註的。

💻 程式範例（Python）

原論文的分類器是另外訓練的小模型。這裡用 claude-sonnet-5 以提示詞當分類器做「Adaptive 風格」的近似：先判斷 A / B / C，再走對應路線；多步路線讓模型每一輪決定要不要再查。retrieve 請換成你自己的檢索器，文件與問題皆為虛構。

import anthropic

client = anthropic.Anthropic()
MODEL = "claude-sonnet-5"
MAX_ROUNDS = 4     # 多步檢索的輪數上限，避免無限循環

def ask(prompt, max_tokens=400):
    msg = client.messages.create(model=MODEL, max_tokens=max_tokens,
        messages=[{"role": "user", "content": prompt}])
    return msg.content[0].text.strip()

# 假設的檢索器：查手冊、工單、CMS 報告，回傳文字片段清單
def retrieve(query, k=3): ...

def classify(question):
    # 複雜度分類器：A 不需檢索、B 單步、C 需跨文件多步
    out = ask("把問題分成 A、B、C 其中一類，只輸出一個字母。\n"
              "A：一般概念，不需查文件。\n"
              "B：查一份手冊就能回答的告警處理題。\n"
              "C：要跨手冊、工單、報告多步推理的根因分析題。\n"
              f"問題：{question}", 5)
    return out[0] if out[:1] in "ABC" else "B"   # 判不出來就退回單步

def answer_with(question, notes):
    ctx = "\n".join(f"- {n}" for n in notes) or "（無）"
    return ask(f"只根據下列資料回答；資料不足就說明不足。\n{ctx}\n問題：{question}")

def adaptive_rag(question):
    route = classify(question)
    if route == "A":
        return ask(question)                       # 不檢索
    if route == "B":
        return answer_with(question, retrieve(question))   # 單步

    # C：多步。每一輪讓模型看已蒐集的資料，決定下一個要查什麼，或宣告足夠
    notes = []
    for _ in range(MAX_ROUNDS):
        nxt = ask(f"問題：{question}\n已蒐集：{notes}\n"
                  "若資料足夠回答，只輸出 DONE；否則輸出下一個要查的搜尋語句。", 60)
        if nxt.startswith("DONE"):
            break
        notes += retrieve(nxt, k=2)
    return answer_with(question, notes)

print(adaptive_rag("WTG-17 的 PT-203 為什麼一直復發，根因是什麼"))

實務上可以用小型分類模型或規則先做粗分，不必每題多花一次大模型呼叫；也要記錄每題實際走了哪條路線，才能回頭用評估集檢查分類器有沒有偏向某一邊。

⚖️ 與前面課程的比較

基礎 RAG（第 001 堂）Self-RAG（第 013 堂）CRAG（第 014 堂）Adaptive RAG（本堂）
決策時機無，每題都檢索一次生成過程中，模型自己決定檢索之後，評估結果好壞檢索之前，依問題難度分流
誰來判斷沒有人微調過的生成模型輕量評估器複雜度分類器（較小的模型）
複雜問題單步，常常答不全逐段檢索與批判補救檢索多步檢索，逐輪整合
主要成本最低要訓練、逐段評審每份文件多一次評估多一個分類器；走多步路線時呼叫次數多

CRAG 在檢索之後把關品質，Adaptive RAG 在檢索之前決定力氣。兩者互補：先分流，單步路線再接 CRAG 的評估，多步路線每一輪也可以檢查結果。更進一步讓模型自己規劃工具與步驟，就是後面會談的 Agentic RAG。

⚠️ Adaptive RAG 常見的坑 / 何時不該用

  • 分類器判錯：把根因分析題當成單步題，答案會缺資料還顯得很有把握。互動範例中輸入含糊的問題就能看到這種情況；上線後要用評估集統計混淆矩陣。
  • 錯誤代價不對稱：分太簡單會答不全，分太複雜只是多花錢。高風險場景（例如涉及安全作業）寧可偏向走複雜路線。
  • 多步檢索要設上限：沒有輪數與費用上限，模型可能一直查下去；也要設停止條件，並在資料仍不足時誠實說明。
  • 「不檢索」路線的風險：模型自身知識可能過時或不適用 OW-8。涉及機型細節、告警代碼、門檻值的題目，不要放進 A 路線。
  • 流量單一時不划算：如果幾乎所有問題都是查單一告警代碼，固定單步加重排序更簡單、更容易除錯；問題類型多樣、成本敏感時才值得加路由。
  • 路由本身要可觀察：把每題的標籤、路線與檢索次數寫進日誌，使用者回報「答不好」時才查得出是分流錯，還是檢索錯。
風場、機型、手冊內容與數據皆為虛構，實際作業以原廠手冊與現場規範為準。互動範例的分類器以規則模擬、檢索為簡化的 TF-IDF；工單、報告與告警代碼僅供教學示範，檢索輪數也是為了說明而設定。

延伸閱讀：Jeong、Baek、Cho、Hwang、Park，〈Adaptive-RAG: Learning to Adapt Retrieval-Augmented Large Language Models through Question Complexity〉（NAACL 2024，arXiv:2403.14403）。

📝 小測驗

Adaptive RAG 的分類器在流程中的哪個時間點運作？

分類器先看問題本身，決定不檢索、單步或多步；檢索後評估文件品質是 CRAG，生成後檢查依據則是 Self-RAG 一類的做法。

技師問「WTG-17 的 PT-203 為什麼一直復發」，卻被分類器判為單步題。最可能的後果是？

複雜題被分到簡單路線，是代價較高的那種錯誤：資料不全卻仍會產生看似合理的答案。因此要用評估集監控分類器，高風險題可偏向走多步。
