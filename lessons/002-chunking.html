切塊 Chunking：一刀切壞，後面全部白費

檢索增強生成的第一步，是把長文件拆成一段段可以被搜尋的片段（chunk）。切錯位置，答案所需的關鍵句子會被拆到兩個片段裡——不管後面接哪一種進階檢索技術，都補不回那段消失的上下文。

🎬 動畫：一句話怎麼被切壞、又怎麼被救回來

🧩 重點整理

固定長度最省事只看字數，不看內容；實作一行程式，索引速度最快，但完全不管句子有沒有被切斷。
重疊是低成本保險相鄰片段共用一段文字（常見 10%–20%），邊界句子至少會完整出現在其中一個片段裡。
遞迴切塊照結構走依段落、句號、逗號的優先順序切，只有片段還是太長才繼續往下一層切——盡量不切句子。
語意切塊照意思走用嵌入模型比對相鄰句子的相似度，話題改變才切；連沒有標點的逐字稿也適用，但索引時要多花運算成本。

🧪 互動範例：親手切一份社區規約

下面是一份虛構的「社區住戶規約」全文（尚未切塊）。切換切塊策略、拖動參數，看看「寵物限重 15 公斤，以下犬貓需登記」這條規則會不會被拆散——以及拆散之後，檢索還能不能找到完整答案。

💻 程式範例（Python）

三種切塊策略的最小實作，不需要額外套件；語意切塊用簡化的相似度邏輯示範概念，實務上會用真的嵌入模型。

# 三種切塊策略的最小實作
import numpy as np

# ① 固定長度 + 重疊：最快、最不看內容
def split_fixed(text, size=80, overlap=20):
    step = max(1, size - overlap)
    return [text[i:i+size] for i in range(0, len(text), step)]

# ② 遞迴切塊：先試著在句號切，句子太長才退而用逗號切
def split_recursive(text, size=80):
    sentences = [s + "。" for s in text.split("。") if s]
    chunks, cur = [], ""
    for s in sentences:
        if len(s) > size:
            if cur:
                chunks.append(cur); cur = ""
            piece = ""
            segs = s.split("，")
            for i, seg in enumerate(segs):
                with_sep = seg + ("，" if i < len(segs) - 1 else "")
                if piece and len(piece + with_sep) > size:
                    chunks.append(piece); piece = with_sep
                else:
                    piece += with_sep
            if piece:
                chunks.append(piece)
            continue
        if cur and len(cur + s) > size:
            chunks.append(cur); cur = s
        else:
            cur += s
    if cur:
        chunks.append(cur)
    return chunks

# ③ 語意切塊：句子先嵌入，相鄰句子相似度低於平均值就切開
def split_semantic(sentences, embed_fn, ratio=0.9):
    vecs = embed_fn(sentences)                          # shape: (n, dim)，已正規化
    sims = [float(vecs[i] @ vecs[i+1]) for i in range(len(vecs) - 1)]
    avg = np.mean(sims)
    chunks, cur = [], sentences[0]
    for i in range(1, len(sentences)):
        if sims[i-1] < avg * ratio:
            chunks.append(cur); cur = sentences[i]
        else:
            cur += sentences[i]
    chunks.append(cur)
    return chunks

⚖️ 四種切塊策略比較

固定長度（無重疊）固定長度＋重疊遞迴切塊語意切塊
索引時的計算成本最低低（片段數變多）低（只需字串處理）高（每句都要跑嵌入模型）
句子被切斷風險高中（視重疊寬度而定）低（照標點、段落切）最低（照話題轉換切）
片段長度固定固定可變可變
實作難度一行程式一行程式需要分隔符優先順序清單需要嵌入模型與門檻調整
適合情境格式規則、追求速度大多數情境的預設起點有清楚段落／標點的文件（手冊、合約）口語逐字稿、缺乏段落的長文

⚠️ 切塊常見的坑 / 何時不該用

  • Overlap 不是越大越好：重疊比例太高，片段數量暴增、內容大量重複，檢索結果容易被幾乎相同的片段佔滿 Top-k，反而稀釋多樣性。常見落點是片段長度的 10%–20%。
  • 遞迴切塊也會失靈：分隔符清單要符合文件結構；面對逐字稿、聊天紀錄這種沒有段落與標點的文字，遞迴切塊最後還是只能照字數硬切，跟固定長度沒兩樣。
  • 語意切塊的門檻很敏感：門檻設太嚴會切出大量瑣碎的小片段，噪音反而變多；設太鬆又會把不相關的話題黏在同一片段裡，而且每次索引都要重新跑一次嵌入模型，成本比前兩者高很多。
  • 片段長度要配合嵌入模型：多數嵌入模型有適合的輸入長度區間，片段太長會讓向量被平均稀釋（什麼都像又什麼都不像），片段太短則缺乏足夠上下文。
  • 別忘了保留中繼資料：不管用哪種策略，每個片段都應該記住來源（文件、頁碼、條號），才能在檢索結果裡附上出處，之後也才能做中繼資料過濾。

📝 小測驗

文件裡有一句話剛好卡在切塊的邊界上，下列何者成本最低、幾乎不用改程式邏輯就能降低它被攔腰打斷的風險？

重疊幾乎不需要改變邏輯，只要在切下一個片段時往回多帶一段字，就能讓邊界句子有機會完整出現在至少一個片段裡；A 會讓片段失去語意，C 在長文件上會超出模型的上下文長度而且成本高昂。

要處理「沒有標點符號、口語化的會議逐字稿」，下列何種切塊策略理論上最適合？

逐字稿常常沒有明確的段落或標點可以依靠，遞迴切塊會退化成跟固定長度一樣的字元硬切；語意切塊直接比較句子意思的相似度，跟有沒有標點無關，因此更能抓到話題轉換的位置。
