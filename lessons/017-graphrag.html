第 017 堂高階約 18 分鐘

GraphRAG：知識圖譜與社群摘要

技師問「旋角系統的故障主要分成哪幾類？彼此怎麼關聯？」手冊把零件、故障模式、告警代碼分散寫在各節，切塊之後，誰連到誰的資訊就丟了。GraphRAG 先請 LLM 從文件抽出實體與關係，連成知識圖譜，再用社群偵測分群、為每個社群寫摘要。區域問題沿著實體的鄰居找，全局問題則讓各社群摘要分頭回答再合併。

🎬 動畫：把手冊建成知識圖譜

🧩 重點整理

圖 + 社群摘要GraphRAG（Edge 等人，Microsoft Research，2024）以 LLM 從切塊抽出實體與關係建圖，再用 Leiden 演算法偵測社群，並為各社群生成摘要。
全局問題用 map-reduce像「手冊整體有哪些主題」這類問題沒有特定實體，所以讓每則社群摘要各出一份部分答案（map），再合併（reduce）。
區域問題走實體鄰居問題中有明確實體時，從該實體出發，取它的相鄰實體、關係與相關切塊，補足「順著關係往外看」的資訊。
索引成本高每個切塊都要抽取實體與關係，每個社群還要寫摘要；文件更新時圖與摘要也要更新。問題多半是單點查詢時不划算。

🧪 互動範例：向量檢索 vs 區域搜尋 vs 全局搜尋

下面是虛構的《OW-8 運維手冊》旋角系統片段：8 個切塊、9 個實體、3 個社群。實體、關係與社群摘要是我事先標註、手寫的（沒有真的呼叫 LLM），向量檢索則是在瀏覽器裡用簡化的 TF-IDF 餘弦相似度真的算。選一個問題與檢索方式，看取回的內容涵蓋了多少「必要的切塊」（社群摘要算涵蓋它底下所有切塊），以及要花幾次 LLM 呼叫。你也可以輸入自己的問題，只是「必要」的標註僅限預設題。

💻 程式範例（Python）

最小實作：用 claude-sonnet-5 從切塊抽取實體與關係，以 networkx 建圖、做社群偵測（Leiden 需另裝 graspologic 或 igraph，這裡改用 networkx 內建的 Louvain 以便執行），再做全局的 map-reduce。先 pip install anthropic networkx。文件與問題皆為虛構；真實系統還會做實體合併、重複抽取（gleaning）與階層式社群。

import json, anthropic, networkx as nx

client = anthropic.Anthropic()
MODEL = "claude-sonnet-5"

# 手冊切塊（虛構）
chunks = [
    "每半年做備援電源放電測試，記錄電容模組電壓；失敗時顯示 PT-230。",
    "PT-230 旋角備援電源測試失敗：檢查電容模組電壓與充電迴路。備援電源負責供電給旋角馬達。",
    "PT-203 旋角馬達過溫：檢查冷卻風扇與風道，量測 PT100 感測器阻值。",
    "冷卻風扇停轉會使旋角馬達散熱不足，持續高負載時出現 PT-203。",
    "PT-205 旋角馬達煞車異常：檢查煞車線圈電阻與煞車間隙。",
    "煞車線圈斷路時煞車無法釋放，旋角馬達轉不動。",
]

def ask(prompt, max_tokens=600):
    msg = client.messages.create(model=MODEL, max_tokens=max_tokens,
        messages=[{"role": "user", "content": prompt}])
    return msg.content[0].text.strip()

# 1) 抽取實體與關係：每個切塊一次 LLM 呼叫
def extract(text):
    raw = ask('從下列段落抽出實體與關係，只輸出 JSON：'
              '{"entities":["名稱"],"relations":[["甲","關係","乙"]]}\n' + text)
    return json.loads(raw[raw.index("{"): raw.rindex("}") + 1])

G = nx.Graph()
for c in chunks:
    r = extract(c)
    G.add_nodes_from(r["entities"])
    for a, rel, b in r["relations"]:
        G.add_edge(a, b, rel=rel)          # 同名實體自然合併成同一個節點

# 2) 社群偵測 + 3) 每個社群一則摘要
communities = nx.community.louvain_communities(G, seed=0)
summaries = []
for members in communities:
    rels = [f"{a}-{d['rel']}-{b}" for a, b, d in G.subgraph(members).edges(data=True)]
    summaries.append(ask("用繁體中文，為下列實體與關係寫一則 80 字內的摘要，"
                          "不要加入沒有的內容：\n" + f"實體：{sorted(members)}\n關係：{rels}"))

# 4) 全局搜尋：map（各社群摘要各答一次）→ reduce（合併）
def global_search(question):
    partial = [ask(f"摘要：{s}\n問題：{question}\n只根據摘要寫出相關的部分答案，沒有相關就回答「無」。")
               for s in summaries]
    partial = [p for p in partial if p != "無"]
    return ask(f"問題：{question}\n把下列部分答案整合成完整答案：\n" + "\n".join(partial))

print(global_search("旋角系統的故障主要分成哪幾類？彼此怎麼關聯？"))

區域搜尋則是：認出問題中的實體，用 G.neighbors(實體) 取鄰居，再把相關切塊、關係與社群摘要放進提示。正式使用時，要抽查抽取出的實體與關係，也要保留每個節點對應的原文切塊，答案才能回溯到出處。

⚖️ 與前面課程的比較

基礎 RAG（第 001 堂）混合檢索（第 004 堂）RAPTOR（第 016 堂）GraphRAG（本堂）
索引的單位原文切塊切塊（向量 + 關鍵字）切塊 + 依語意分群的摘要樹切塊 + 實體關係圖 + 社群摘要
擅長的問題單一事實精確詞與語意並重整合多段的全局問題跨文件的關係與全局主題
分群依據無無嵌入向量相近圖上連線的密度（Leiden）
建索引成本最低低每群一次摘要，逐層遞迴每個切塊抽取 + 每個社群摘要，最高

RAPTOR 與 GraphRAG 都用 LLM 摘要回答全局問題，差別在分群的依據：RAPTOR 看文字語意相近，GraphRAG 看實體之間有沒有關係，所以更適合「零件—故障—告警」這種本來就有結構的知識。

⚠️ GraphRAG 常見的坑 / 何時不該用

  • 抽取會出錯：LLM 可能漏抽實體、把同一個零件的不同寫法當成兩個，或抽出不存在的關係。圖建好後要抽查，並做實體合併。
  • 索引成本高：每個切塊至少一次抽取呼叫，每個社群再一次摘要呼叫。語料大時要先估算時間與費用。
  • 全局查詢也貴：map 階段每個社群一次呼叫，社群越多越慢、越貴；可只用較高層級的社群來省成本。
  • 單點問題不划算：查單一告警代碼、單一料號，混合檢索加重排序更簡單、更便宜、更精準。
  • 摘要會省略細節：社群摘要可能略掉門檻值或安全步驟。涉及作業安全時，答案仍要回到原文切塊核對。
  • 文件更新要重做：新增或修改手冊後，相關實體、關係與社群摘要都可能過時，要規劃增量更新或定期重建。
風場、機型、手冊內容與數據皆為虛構，實際作業以原廠手冊與現場規範為準。互動範例的實體、關係與摘要為事先手寫、檢索為簡化的 TF-IDF，告警代碼與故障關聯僅供教學示範。

延伸閱讀：Edge、Trinh、Cheng、Bradley、Chao、Mody、Truitt、Metropolitansky、Ness、Larson，〈From Local to Global: A Graph RAG Approach to Query-Focused Summarization〉（Microsoft Research，2024，arXiv:2404.16130）。

📝 小測驗

GraphRAG 的索引階段，大致依什麼順序進行？

先用 LLM 從切塊抽出實體與關係並建成圖，再偵測社群，最後為各社群寫摘要，查詢時才用到這些摘要與圖。

「旋角系統的故障主要分成哪幾類」這種全局問題，GraphRAG 怎麼處理？

全局問題沒有特定實體可抓，所以對各社群摘要做 map-reduce，涵蓋面廣。代價是 map 階段每個社群都要一次 LLM 呼叫。
