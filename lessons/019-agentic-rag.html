第 019 堂高階約 20 分鐘

Agentic RAG：讓代理人規劃多步檢索

遠端監控中心問：「WTG-17 的旋角告警何時能出海修？要備什麼料？」答案散在 SCADA 告警、運維手冊、備品表、天候預報裡，而且後一步要查什麼，取決於前一步查到什麼（先知道告警代碼，才能查手冊；先知道料號，才能查庫存）。一般 RAG 只用原問題檢索一次，做不到。Agentic RAG 把各種檢索包成工具，交給 LLM 代理人（agent）自己規劃：思考還缺什麼、呼叫工具、讀結果，重複到資訊足夠才回答。

🎬 動畫：代理人一步步把資訊湊齊

🧩 重點整理

檢索變成工具每種資料源（SCADA、手冊、備品表、天候、工單）是一個工具，有名稱、說明與參數；LLM 依說明決定要不要呼叫、怎麼下查詢。
思考、行動、觀察迴圈每一輪根據目前已知資訊決定下一步，把結果加進上下文再繼續；這個交錯推理與行動的做法在 ReAct 論文中提出。
解決多步（multi-hop）問題後一步的查詢常來自前一步的結果；代理人也能在查不到時改寫查詢、換工具，或判斷資訊已足夠而停止。
用彈性換成本與風險呼叫次數、延遲與花費都較高，也可能查錯或繞圈；需要步數上限、停止條件與紀錄，簡單問題仍用單次檢索。

🧪 互動範例：單次 RAG vs 代理人迴圈

下面有 5 個虛構的資料源（SCADA、手冊、備品表、天候、工單）。這裡的「代理人」不是真的 LLM，而是一段寫死的規劃規則：它依「還缺哪項資訊」選工具，用 BM25 在該工具的資料裡檢索，並從上一步的結果解析出告警代碼、料號與風速門檻，再組出下一步的查詢。單次 RAG 則把所有資料混在一起，用原問題檢索一次，取前 3 筆。請切換問題與模式，調整「步數上限」，看必要資訊湊齊了幾項。真實代理人由 LLM 決定每一步，行為會更有彈性，也更難預測。

💻 程式範例（Python）

用 anthropic SDK 的工具呼叫（tool use）寫出最小的代理人迴圈：把每個資料源宣告成工具，模型回傳 tool_use 就執行並把結果送回，直到它不再呼叫工具為止（pip install anthropic）。資料與問題皆為虛構，檢索用最簡單的關鍵字比對代替真正的檢索系統。

import anthropic

client = anthropic.Anthropic()
MAX_STEPS = 6                                   # 步數上限：防止無限迴圈

# 1) 虛構資料源：每個工具對應一份資料
SOURCES = {
    "search_scada": ["2026-10-11 06:12 WTG-17 PT-205 旋角馬達煞車異常，葉片 2"],
    "search_manual": ["PT-205 煞車異常：更換煞車線圈 PT-BRK-05；進輪轂須風速低於 12 m/s"],
    "search_parts": ["PT-BRK-05 旋角馬達煞車線圈，港區倉庫庫存 2 件"],
    "search_weather": ["2026-10-12 上午 風速 9 m/s 浪高 0.8 m", "2026-10-13 全日 風速 16 m/s 浪高 2.3 m"],
}
TOOLS = [{
    "name": name,
    "description": f"在「{name[7:]}」資料中用關鍵字檢索，回傳符合的紀錄",
    "input_schema": {"type": "object", "properties": {"query": {"type": "string"}}, "required": ["query"]},
} for name in SOURCES]

def run_tool(name, query):
    words = query.split()
    hits = [d for d in SOURCES[name] if any(w in d for w in words)]
    return "\n".join(hits) or "查無資料"

# 2) 代理人迴圈：思考 → 行動（呼叫工具）→ 觀察（結果送回）
messages = [{"role": "user", "content":
    "WTG-17 的旋角告警何時能出海修？要備什麼料？請先用工具查證，再回答並註明出處。"}]
for step in range(MAX_STEPS):
    resp = client.messages.create(model="claude-sonnet-5", max_tokens=1024,
                                  tools=TOOLS, messages=messages)
    if resp.stop_reason != "tool_use":               # 模型認為資訊夠了，直接回答
        print(resp.content[0].text)
        break
    messages.append({"role": "assistant", "content": resp.content})
    results = [{"type": "tool_result", "tool_use_id": b.id,
                "content": run_tool(b.name, b.input["query"])}
               for b in resp.content if b.type == "tool_use"]
    messages.append({"role": "user", "content": results})
else:
    print("步數用完仍未收斂：改請人工處理或回報目前已知資訊")

注意：上面的關鍵字比對只是為了讓程式能直接跑；實務上每個工具背後可以是向量檢索、混合檢索（第 004 堂）或資料庫查詢。也要記錄每一步的工具與查詢，方便事後檢查代理人為什麼這樣查。

⚖️ 與前面課程的比較

基本 RAG（第 001 堂）Self-RAG / CRAG（第 013、014 堂）Adaptive RAG（第 015 堂）Agentic RAG（本堂）
誰決定流程固定：檢索一次再生成固定流程，加上評估與修正分類器依問題難度挑流程LLM 每一步自己決定
資料來源單一知識庫知識庫，可補網路搜尋知識庫或多步流程多個工具，彼此串接
能否用上一步結果查下一步不能有限（改寫查詢重查）多步流程可以可以，是主要用途
成本與可預測性最低、最穩定中依分類結果而定最高，步數與花費不固定

可以把它們看成光譜：流程越固定越便宜、越好測試；交給 LLM 決定越多越有彈性，也越難控管。能用固定流程解決的問題，不必上代理人。

⚠️ Agentic RAG 常見的坑 / 何時不該用

  • 延遲與花費變成好幾倍：每一輪都是一次 LLM 呼叫，加上工具執行。現場技師要的是幾秒內的答案時，要評估是否值得。
  • 可能繞圈或查錯方向：重複下同樣的查詢、被無關結果帶偏。要設步數上限、偵測重複呼叫，並在用完步數時誠實回報「尚未查清」。
  • 工具描述寫不好就選錯工具：工具名稱、用途與參數說明要清楚，且彼此職責不重疊。
  • 錯誤會一路累積：第一步查錯風機或告警，後面全部建立在錯的前提上。關鍵識別（風機編號、料號）要在輸出中明確顯示，必要時請人確認。
  • 有副作用的工具要把關：查詢類工具可放手讓它跑；建立工單、調整參數這類會改變系統的動作，應該人工確認，且不要在現場安全相關決策上由代理人自行拍板。
  • 難以測試與重現：同一個問題可能走出不同路徑。要記錄完整軌跡，並用評估集檢查（見後續的 RAG 評估）。
  • 簡單問題不需要：「PT-205 是什麼告警」查一次手冊即可，用單次檢索或第 015 堂的路由更划算。
風場、機型、手冊內容與數據皆為虛構，實際作業以原廠手冊與現場規範為準。互動範例的「代理人」是寫死的規則而非 LLM，風速門檻、庫存、預報與工單皆為虛構示範，不可作為實際出海或維修決策依據。

延伸閱讀：Yao 等，〈ReAct: Synergizing Reasoning and Acting in Language Models〉（ICLR 2023，arXiv:2210.03629）；Singh 等，〈Agentic Retrieval-Augmented Generation: A Survey on Agentic RAG〉（arXiv:2501.09136）；Anthropic，〈Building effective agents〉（2024，建議從簡單的固定流程開始，確有需要才增加代理人的自主程度）。

📝 小測驗

下列哪種問題最適合用 Agentic RAG，而不是單次檢索？

C 需要先查現況告警，再用結果查手冊、備品與天候，下一步取決於上一步的結果。A、B 查一次就能答，單次檢索更快更便宜。

部署代理人式的檢索時，下列哪項做法最合理？

代理人可能繞圈、查錯或累積錯誤，所以要限制步數、保留軌跡並把關有副作用的動作。把資料源合併成單一工具就失去「依結果規劃下一步」的意義。
