第 009 堂進階約 12 分鐘

情境化檢索：替每個片段加上文件脈絡

文件切成片段後，片段常常脫離了它原本的上下文：「依上節步驟拆下馬達後，依扭力表鎖緊螺栓」——哪個機型？旋角還是偏航？「上節」是哪一節？向量與關鍵字都只看得到片段本身，於是各份手冊裡長得一樣的片段分數幾乎相同。情境化檢索（Contextual Retrieval）在建索引前，先請 LLM 替每個片段寫一兩句「它在整份文件中的位置」，接在片段前面，再做嵌入與 BM25，讓片段自己就帶著脈絡。

🎬 動畫：三個長得一樣的片段，靠「情境」分出誰是誰

🧩 重點整理

問題出在「脫離上下文」切塊後，片段常不再寫明所屬機型、子系統或章節。向量與關鍵字都只看片段本身，不同手冊裡長得像的片段就難以分辨。
索引時補脈絡用 LLM 讀整份文件，為每個片段生成一兩句情境，接在片段前再建索引。這是 Anthropic 於 2024 年提出的做法，包含情境化嵌入與情境化 BM25 兩部分。
一次性成本每個片段要呼叫一次 LLM，但整份文件可用提示詞快取（prompt caching）重複利用。Anthropic 在其假設下（800 token 片段、100 token 情境）估算約每百萬文件 token 1.02 美元。
可與其他技術疊加Anthropic 的評測中，Top-20 失敗率由 5.7% 降到 3.7%（情境化嵌入）、2.9%（再加 BM25）、1.9%（再加重排序）。數字來自其資料集，換成你的資料要自己量。

🧪 互動範例：原片段 vs. 情境化片段

下面是虛構的《OW-8 運維手冊》與舊款《OW-6 運維手冊》共 8 個片段，其中有好幾組字面幾乎相同的片段。選一個問題，切換三種索引方式：原片段（嵌入）、情境化片段（嵌入）、情境化 + BM25 混合（RRF）。每個片段前的情境是人工預先寫好的，模擬 LLM 的輸出。「正解」是技師真正需要的那一個片段，下方會顯示它排第幾名、有沒有進 Top-N。檢索用簡化的 TF-IDF 與 BM25 模擬，不是真正的嵌入模型。

💻 程式範例（Python）

手動實作情境化檢索：索引時對每個片段呼叫 claude-sonnet-5 生成情境（整份文件放在可快取的區塊），把「情境 + 片段」同時送進嵌入與 BM25；查詢時兩路各取前幾名，再用 RRF 融合。範例文件為虛構。

import numpy as np
from rank_bm25 import BM25Okapi
from sentence_transformers import SentenceTransformer
import anthropic

client = anthropic.Anthropic()
embedder = SentenceTransformer("BAAI/bge-m3")

# ① 原始文件與切好的片段（虛構的 OW-8 手冊；片段本身看不出機型與子系統）
doc = "《OW-8 運維手冊》6.3 旋角馬達更換程序：安全前置、拆卸、安裝、復歸測試……"
chunks = ["依上節步驟拆下馬達後，依扭力表分次對角鎖緊固定螺栓。", "……"]

# ② 索引階段：請 LLM 替每個片段寫情境（整份文件放進可快取的區塊）
def situate(doc, chunk):
    msg = client.messages.create(
        model="claude-sonnet-5", max_tokens=200,
        messages=[{"role": "user", "content": [
            {"type": "text", "text": f"<document>\n{doc}\n</document>",
             "cache_control": {"type": "ephemeral"}},
            {"type": "text", "text": f"以下是要放回整份文件中的片段：\n<chunk>\n{chunk}\n</chunk>\n"
                                "請用一兩句簡短的情境說明這個片段在整份文件中的位置，以利檢索。只回答情境。"},
        ]}])
    return msg.content[0].text.strip()

contextualized = [f"{situate(doc, c)}\n{c}" for c in chunks]

# ③ 兩份索引都用「情境 + 片段」：嵌入 + BM25（中文用二元組當 token）
def toks(t):
    t = t.lower()
    return [t[i:i+2] for i in range(len(t) - 1)]

vecs = embedder.encode(contextualized, normalize_embeddings=True)
bm25 = BM25Okapi([toks(c) for c in contextualized])

# ④ 查詢：兩路各取前 k 名，用 RRF 融合
def search(question, k=20, top=3):
    q = embedder.encode([question], normalize_embeddings=True)[0]
    by_vec = np.argsort(-(vecs @ q))[:k]
    by_bm25 = np.argsort(-bm25.get_scores(toks(question)))[:k]
    score = {}
    for ranking in (by_vec, by_bm25):
        for rank, i in enumerate(ranking):
            score[i] = score.get(i, 0) + 1 / (60 + rank + 1)
    best = sorted(score, key=score.get, reverse=True)[:top]
    return [contextualized[i] for i in best]

for hit in search("OW-8 旋角馬達更換，螺栓怎麼鎖？"):
    print(hit, "\n---")

一般檢索（第 001 堂）混合檢索（第 004 堂）父子檢索（第 008 堂）情境化檢索（本堂）
改動的階段—檢索時合併兩路排名索引小塊、回傳大塊索引前先改寫片段
解決什麼基本的語意檢索語意與精確詞各有盲點精準與完整的兩難片段脫離上下文、難以分辨
額外成本無多維護一份 BM25 索引多一個 docstore；LLM 讀入變多每個片段一次 LLM 呼叫；文件更新要重算
主要風險相似片段難區分仍看不到片段外的脈絡父段落夾帶無關內容情境寫錯會污染索引

⚠️ 情境化檢索常見的坑 / 何時不該用

  • 情境寫錯會污染索引：LLM 可能把 OW-8 寫成 OW-6，或編出文件裡沒有的資訊。情境應只依文件內容，並抽樣檢查；風險高的領域可由程式直接把章節標題、機型欄位拼進去，不依賴 LLM。
  • 索引成本與更新：每個片段都要呼叫一次 LLM，文件改版時受影響的片段要重新生成。用提示詞快取可大幅降低成本，但仍要先估算文件量。
  • 情境不要太長：情境太長會稀釋片段本身的語意，也浪費索引空間。要求「簡短」即可，通常一兩句就夠。
  • 片段本來就自足就不必做：像 FAQ、單一告警代碼條目這類每段都完整寫明主角的文件，補情境的效益有限。
  • 知識庫很小可以直接放進上下文：Anthropic 的文章指出，知識庫小於約 20 萬 token（約 500 頁）時，可考慮直接放進提示詞，不一定要建檢索（路線圖中的「長上下文 vs RAG」會再討論）。
範例中的鷗灣離岸風場、OW-8／OW-6 機型、運維手冊內容、章節編號與告警代碼皆為虛構，僅供教學示範；互動範例使用簡化的 TF-IDF 與 BM25 模擬，情境為人工預寫；實際作業以原廠手冊與現場規範為準。

📝 小測驗

情境化檢索的「情境」是在什麼時候、由誰產生的？

情境化檢索發生在索引階段：每個片段先被補上「它在整份文件中的位置」，再做嵌入與 BM25。查詢時不需要再呼叫 LLM，所以成本是一次性的、與查詢量無關。

為什麼情境化後，BM25 也要用「情境 + 片段」來建索引？

BM25 只比對字面。片段若沒寫「OW-8」，查詢中的「OW-8」就無法加分；把情境接上去，精確詞才會出現在索引裡。這也是 Anthropic 將情境化同時用於嵌入與 BM25 的原因。
