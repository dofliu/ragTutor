第 007 堂進階約 12 分鐘

HyDE：先生成假設答案，再用它去檢索真實文件

現場技師的問句常是口語描述症狀（「馬達好像很燙」），手冊寫的卻是技術術語（「旋角馬達過溫」），兩邊幾乎沒有共同詞彙，檢索容易落空。HyDE（Hypothetical Document Embeddings，假設文件嵌入）先讓 LLM 憑印象寫一段「假設的答案」，再拿這段話的向量去找真實文件——用「答案找答案」，取代「問題找答案」。

🎬 動畫：從口語問句，到用假設答案找到真實手冊段落

🧩 重點整理

問句和答案是兩種文體技師用症狀描述提問，手冊用技術術語作答；直接拿問句的向量去比，容易比到語意鬆散的泛用段落。
用「答案找答案」HyDE 先讓 LLM 寫出假設文件（原論文為 Gao 等人 2022），再用這份假設文件的向量檢索，讓查詢向量落在真實答案段落附近。
編造的細節不是致命傷假設文件只用來產生查詢向量，不會出現在最終答案；編碼器只保留語意的特性，會淡化部分錯誤細節。
多寫幾份更穩論文的做法是生成多份假設文件，把它們的向量（連同原問句）取平均，降低單次生成走偏的風險。

🧪 互動範例：問句 vs. 假設文件

下面是《OW-8 運維手冊》旋角系統與相鄰章節共 13 個段落。選一句技師的口語問句，比較三種查詢方式的檢索結果；「假設文件」是預先寫好的示範文字，模擬 LLM 會生成的內容（本網站不會呼叫真正的語言模型），你也可以直接改寫它，看看寫偏了會發生什麼事。第 4 個範例刻意讓假設文件猜錯方向。

💻 程式範例（Python）

用 anthropic SDK 為技師的問句生成 3 份假設文件，以 sentence-transformers 編碼後與原問句的向量取平均，再檢索真實手冊段落。生成的假設文件只用來檢索，最後回答仍以真實段落為依據。

import numpy as np
from sentence_transformers import SentenceTransformer
import anthropic

# ① 索引階段：手冊段落先算好向量（範例文件為虛構）
embedder = SentenceTransformer("BAAI/bge-m3")
chunks = [
    "告警 PT-203 旋角馬達過溫：馬達繞組溫度超過保護門檻時，控制器限制電流……",
    "告警 PT-205 旋角馬達煞車異常：煞車釋放或吸合訊號與指令不符時觸發……",
    "旋角減速機保養：每年檢查減速機油位與油色……",
]
chunk_vecs = embedder.encode(chunks, normalize_embeddings=True)
client = anthropic.Anthropic()

# ② HyDE：讓 LLM 寫「假設的手冊段落」，不需要正確，只要長得像
def hypothetical_docs(question, n=3):
    prompt = (f"你是風機運維手冊的作者。針對技師的問題：「{question}」\n"
              "請寫一段手冊風格的故障排除說明（約 100 字），"
              "使用手冊常見術語；細節不確定也沒關係。只輸出說明本文。")
    docs = []
    for _ in range(n):                      # 每次取樣結果不同
        msg = client.messages.create(model="claude-sonnet-5", max_tokens=300,
                                     messages=[{"role": "user", "content": prompt}])
        docs.append(msg.content[0].text)
    return docs

# ③ 檢索：假設文件的向量（連同原問句）取平均，再找真實段落
def hyde_retrieve(question, top_n=3):
    texts = [question] + hypothetical_docs(question)
    vecs = embedder.encode(texts, normalize_embeddings=True)
    q = vecs.mean(axis=0)
    q /= np.linalg.norm(q)
    scores = chunk_vecs @ q
    top = np.argsort(-scores)[:top_n]
    return [chunks[i] for i in top]              # 只回傳真實段落

# ④ 生成：依真實段落回答，假設文件不進入 prompt
def answer(question):
    context = "\n".join(f"[{i+1}] {c}" for i, c in enumerate(hyde_retrieve(question)))
    prompt = f"參考資料：\n{context}\n\n問題：{question}\n請只依參考資料回答；資料中沒有就說不知道。"
    msg = client.messages.create(model="claude-sonnet-5", max_tokens=512,
                                 messages=[{"role": "user", "content": prompt}])
    return msg.content[0].text

print(answer("葉片轉不動，馬達好像很燙"))

⚖️ 四種做法比較

原始問句直接檢索查詢改寫 / Multi-Query（第 006 堂）HyDE（本堂）重排序（第 005 堂）
額外 LLM 呼叫無1 次（生成改寫查詢）1 次或多次（生成假設文件）無 LLM，但多一次 cross-encoder 運算
解決什麼—問句模糊、原因不只一種問句與答案段落的用詞、文體落差候選段落的排序不夠準
適合情境問句已含精確術語或代碼要涵蓋多個子系統的可能原因口語描述症狀、想找的是說明性段落召回已含正解、只差排序
主要風險口語問句容易落空改寫可能編造不存在的術語模型不懂該領域時，假設文件可能整段偏題不能找回召回階段漏掉的段落

⚠️ HyDE 常見的坑 / 何時不該用

  • LLM 不熟悉的領域容易寫偏：模型沒看過你的手冊，只能憑一般常識猜。猜對方向（過溫）就有效；猜錯方向（例如把「很燙」寫成煞車問題），檢索反而被帶偏——互動範例的第 4 題就是這種情況。
  • 每次查詢多一次生成，延遲與成本上升：多生成幾份假設文件更穩，但成本也線性增加；即時性要求高的場景要評估。
  • 精確代碼、料號查詢不需要：使用者直接輸入「PT-203」時，關鍵字檢索（BM25）就能精準命中，先生成假設文件只是多花時間，還可能被編造的內容干擾。
  • 假設文件不能當答案或證據：它可能含編造的代碼與門檻值。最終回答必須依檢索到的真實段落，並附出處。
  • 問句本來就精確時效益有限：原論文的實驗也顯示，對已在大量有標註資料上微調過的檢索器，HyDE 的優勢會縮小；先用第 001–006 堂的方法把基礎打好，再評估是否值得加。
範例中的鷗灣離岸風場、OW-8 機型、運維手冊內容、告警代碼皆為虛構，僅供教學示範；互動範例中的「假設文件」為預先寫好的示範文字，並非真正呼叫語言模型產生，檢索使用的是簡化的 TF-IDF 模擬；實際作業以原廠手冊與現場規範為準。

📝 小測驗

HyDE 生成的假設文件可能含有編造的細節，為什麼這種做法仍然有用？

HyDE 的價值不在假設文件「對不對」，而在它「長得像」手冊裡的答案段落，讓查詢向量更靠近真實答案。編造的細節會被嵌入模型淡化，而且假設文件不會進入最終答案，回答仍以真實檢索到的段落為依據。

下列哪種情況最不適合使用 HyDE？

代碼是精確的關鍵字，用 BM25 就能直接命中，先生成假設文件只會增加延遲，還可能被編造內容干擾。B、C 則是 HyDE 最能發揮的情境：問句與答案用詞落差大，且模型能猜到大致方向。
