延遲切塊 Late Chunking：先嵌入整份文件，再切塊

手冊裡常寫「該馬達的冷卻風扇要先檢查」，前一句才說這是旋角馬達。傳統做法先切塊、再逐塊嵌入，「該馬達」那一塊單獨看不出指的是誰。延遲切塊（Late Chunking）把順序反過來：先讓長上下文嵌入模型讀完整份文件、為每個 token 產生向量，再依切塊邊界做平均池化，於是每個片段的向量都帶著全文脈絡。

🎬 動畫：把「切」放到嵌入之後

🧩 重點整理

問題：切下去就斷了脈絡手冊常用「該馬達」「上述步驟」「同前」指代前文。逐塊嵌入時，模型看不到前一塊，向量裡就缺少「這是旋角馬達」的訊號。
做法：先嵌入，後池化長上下文嵌入模型一次讀完整份文件，輸出每個 token 的向量；再依切塊邊界，對各片段範圍內的 token 向量做平均池化（mean pooling），得到片段向量。
特色：不改文字、不加 LLM片段文字與原本相同，不需要像情境化檢索（第 009 堂）那樣呼叫 LLM 產生脈絡；原論文指出此法不需額外訓練即可套用在多種長上下文嵌入模型，另提出微調做法。
條件：模型要撐得住長文件必須用能輸出 token 向量的長上下文嵌入模型，文件長度受模型上限限制；是否真的變準，要在自己的資料上評估。

🧪 互動範例：調整脈絡強度，比較先切塊與延遲切塊

下面是虛構《OW-8 運維手冊》中三個章節，每章第一句點名子系統，後面的句子用「該馬達」「該系統」「該軸承」指代。每個句子是一個片段。選一個問題，比較先切塊再嵌入（每塊只看自己的字）與延遲切塊的 Top-k。

這是簡化模擬，不是真的 Transformer：延遲切塊的片段向量＝片段自己的詞向量＋「脈絡強度」×（全文其他位置詞向量，依距離衰減加權）。「脈絡範圍」越大，越遠的句子也算進脈絡。真實模型是用注意力學出脈絡，行為不會這麼單純。試試「旋角馬達更換前要做什麼」：先切塊的 Top-3 會混進別章的片段。

先切塊再嵌入（每塊獨立）
延遲切塊（帶全文脈絡）

💻 程式範例（Python）

用 Hugging Face transformers 做最小的延遲切塊（pip install transformers torch）。重點在三步：整份文件一次過模型、取最後一層的 token 向量、依字元邊界換算成 token 範圍後平均。範例模型名稱請換成你實際使用、支援長輸入的嵌入模型（需允許 trust_remote_code 時請先確認來源）；文件內容為虛構。回答階段用 anthropic SDK。

import numpy as np, torch, anthropic
from transformers import AutoModel, AutoTokenizer

EMB_MODEL = "你的長上下文嵌入模型"   # 例如 Jina 的長上下文嵌入模型（以官方文件為準）
tok = AutoTokenizer.from_pretrained(EMB_MODEL)
model = AutoModel.from_pretrained(EMB_MODEL).eval()

# 虛構的《OW-8 運維手冊》片段；每句一塊，邊界以字元位置記錄
SENTS = [
    "PT-203 旋角馬達過溫的排除步驟如下。",
    "該馬達的冷卻風扇與濾網要先檢查。",
    "降溫後方可復歸，重複發生時須更換該馬達。",
    "更換前必須先執行上鎖掛牌。",
]
DOC = "".join(SENTS)
spans, pos = [], 0
for s in SENTS:
    spans.append((pos, pos + len(s))); pos += len(s)

def late_chunk_embed(doc, spans):
    enc = tok(doc, return_tensors="pt", return_offsets_mapping=True, truncation=True)
    offsets = enc.pop("offset_mapping")[0].tolist()   # 每個 token 對應的字元範圍
    with torch.no_grad():
        token_vecs = model(**enc).last_hidden_state[0]  # 1) 整份文件一次過模型
    out = []
    for a, b in spans:                               # 2) 依邊界取該段的 token
        ids = [i for i, (s, e) in enumerate(offsets) if e > s and s >= a and e <= b]
        v = token_vecs[ids].mean(dim=0)                 # 3) 平均池化
        out.append((v / v.norm()).numpy())
    return np.stack(out)

CHUNK_VECS = late_chunk_embed(DOC, spans)

def embed_query(q):
    enc = tok(q, return_tensors="pt")
    with torch.no_grad():
        v = model(**enc).last_hidden_state[0].mean(dim=0)
    return (v / v.norm()).numpy()

question = "旋角馬達更換前要做什麼？"
scores = CHUNK_VECS @ embed_query(question)
top = [SENTS[i] for i in np.argsort(-scores)[:3]]

client = anthropic.Anthropic()
resp = client.messages.create(
    model="claude-sonnet-5", max_tokens=400,
    messages=[{"role": "user", "content":
        "只根據下列手冊片段回答。\n" + "\n".join(top) + f"\n\n問題：{question}"}])
print(resp.content[0].text)

注意：上面的 truncation=True 會把超過模型上限的部分截掉，實務上要先確認文件長度，過長就先分成較大的段落再各自處理。片段送給 LLM 的仍是原文，脈絡只存在於向量裡。

固定切塊（第 002 堂）父子文件（第 008 堂）情境化檢索（第 009 堂）延遲切塊
做法切好再逐塊嵌入小塊檢索，回傳較大的父塊用 LLM 替每塊補一段脈絡文字，再嵌入與建索引整份文件過嵌入模型，再依邊界池化
優點簡單、通用檢索精準又保有上下文脈絡以文字形式存在，關鍵字檢索也受惠不呼叫 LLM、不改文字；向量帶有全文脈絡
缺點代名詞與省略的片段失去脈絡父塊較大，輸入量增加索引時 LLM 呼叫成本高需長上下文嵌入模型；文件長度受限；脈絡只在向量裡，BM25 看不到
索引成本低低高（大量 LLM 呼叫）中（長輸入的嵌入運算）
適合用在結構清楚、每塊自成一體要把周邊內容一起給模型片段缺脈絡且預算足夠手冊常以「該」「上述」指代、想省 LLM 成本

⚠️ 延遲切塊常見的坑 / 何時不該用

  • 模型不支援就做不到：必須能輸出 token 層級向量、且接受長輸入。只提供「文字進、向量出」的 API 無法在中間取 token 向量。
  • 文件超過上限被截斷：截掉的部分根本沒被嵌入。先量長度，過長就先分段；段與段之間的脈絡不會共享。
  • 每塊本來就自成一體時效益有限：像一條一條獨立的告警代碼表，不太需要前後文，用普通切塊即可。
  • 只改善向量，不改善文字：BM25 與送給 LLM 的片段仍是原文；要讓關鍵字檢索也看到脈絡，可搭配情境化檢索（第 009 堂）或混合檢索（第 004 堂）。
  • 沒有評估就上線：原論文報告在多個基準上有小幅提升，但實際幅度依模型與資料而異。用自己的評估集（第 021 堂）比較召回，再決定值不值得改索引流程。
  • 無關內容的脈絡也會混進來：整份文件塞很多不同主題時，脈絡可能稀釋或誤導。依章節分開處理常比整本一次處理更穩。
  • 安全步驟不能只靠排名：上鎖掛牌、高處作業等必要步驟應由規則強制附帶，不要期待檢索自己撈到。
風場、機型、手冊內容與數據皆為虛構，實際作業以原廠手冊與現場規範為準。互動範例是簡化模擬，分數與排名不代表真實嵌入模型的表現。

延伸閱讀：Günther 等，〈Late Chunking: Contextual Chunk Embeddings Using Long-Context Embedding Models〉（arXiv:2409.04701，Jina AI 等）。

📝 小測驗

延遲切塊裡的「延遲」指的是什麼？

延遲的是「切」：邊界套用在 token 向量上，而不是套用在原始文字上。C 是情境化檢索的做法。

下列哪個情況最不適合直接用延遲切塊？

延遲切塊需要取得 token 層級向量再自行池化；只回傳整段向量的介面做不到。A、B 正是它擅長的情境。
