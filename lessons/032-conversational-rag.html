對話式 RAG：多輪追問先改寫成獨立問題

技師問完「PT-203 旋角馬達過溫怎麼處理」，接著問「那進輪轂之前有什麼安全步驟？」，人一看就懂，檢索系統卻只看到一句沒有主詞的話。多輪對話的追問常有代名詞、省略與接續，直接拿去檢索會失敗。對策是先用對話歷史把追問改寫成不看上下文也讀得懂的獨立問題（standalone question），再交給檢索；回答時則仍然帶著對話歷史。

🎬 動畫：把追問補成完整的問題

🧩 重點整理

追問不能單獨檢索「那 OW-6 呢？」「它的料號？」依賴前面的輪次。檢索系統只看輸入的那一句，沒有主題、機型與告警代碼，就找不到對的段落。
改寫成獨立問題把對話歷史與新問題交給 LLM，要求補上指代對象與省略的條件，只改寫、不回答。這是 QReCC 等研究中 question rewriting 的做法，也是 LangChain history-aware retriever 的核心。
檢索與生成用不同輸入檢索要單句、資訊完整；生成要帶對話歷史才接得上話。兩個階段各取所需，改寫之後的檢索管線完全不用改。
改寫也會出錯漏掉機型、把已經換掉的話題硬接回去，都會讓檢索偏掉。要求保留機型與代碼、讓使用者看得到改寫句，並可同時檢索原句與改寫句再融合。

🧪 互動範例：同一個追問，四種處理方式

💻 程式範例（Python）

condense 用 anthropic 的 claude-sonnet-5 把追問改寫成獨立問題；沒有歷史時直接回傳原句。retrieve_with_history 檢索用改寫句，回答時則把歷史一起交給模型。檢索函式用最簡單的字元重疊示意，實務上請換成前面課程的混合檢索與重排序。

import anthropic

client = anthropic.Anthropic()

DOCS = [
    "PT-203 旋角馬達過溫（OW-8）：檢查冷卻風扇與散熱片積塵，量測馬達繞組溫度。",
    "PT-203 作業安全（OW-8）：進入輪轂前先順槳、鎖定葉輪，並執行上鎖掛牌（LOTO）。",
    "旋角馬達備品（OW-8）：料號 PT-MTR-02，更換時需同時檢查編碼器線路。",
    "PT-203 旋角馬達過溫（OW-6）：舊款機型，檢查馬達冷卻風道與溫度感測器。",
]

def retrieve(query, k=2):
    """示意：以查詢字元與段落的重疊數排序；請換成混合檢索與重排序"""
    score = lambda d: len(set(query) & set(d))
    return sorted(DOCS, key=score, reverse=True)[:k]

def condense(history, question):
    """把追問改寫成獨立問題；history 是 [{"role":..., "content":...}, ...]"""
    if not history:
        return question
    msg = client.messages.create(
        model="claude-sonnet-5", max_tokens=200,
        system="你是查詢改寫器。根據對話歷史，把使用者最後一個問題改寫成不看歷史也讀得懂的獨立問題："
               "補上代名詞指的對象、機型與告警代碼；若問題已經獨立或換了話題，原句輸出；只輸出問題，不要回答。",
        messages=history + [{"role": "user", "content": question}],
    )
    return msg.content[0].text.strip()

def retrieve_with_history(history, question):
    standalone = condense(history, question)
    print(f"改寫後：{standalone}")             # 記錄下來，方便稽核與除錯
    ctx = "\n".join(retrieve(standalone))  # 檢索用改寫句
    msg = client.messages.create(            # 生成仍帶對話歷史
        model="claude-sonnet-5", max_tokens=300,
        messages=history + [{"role": "user", "content":
            f"只根據下列手冊段落回答。\n\n{ctx}\n\n問題：{question}"}],
    )
    return msg.content[0].text

history = [
    {"role": "user", "content": "WTG-07 出現 PT-203，旋角馬達過溫怎麼處理？"},
    {"role": "assistant", "content": "先檢查冷卻風扇與散熱片積塵，並量測馬達繞組溫度。"},
]
print(retrieve_with_history(history, "那進輪轂之前有什麼安全步驟？"))

正式系統建議把原問題、改寫句與檢索結果一起寫進日誌，才能追查「為什麼找到這段」。

⚠️ 對話式 RAG 常見的坑 / 何時不該用

  • 把整段歷史直接拼進檢索：越長越雜，早期的話題會稀釋當前問題。只當備案，不當預設。
  • 改寫漏掉關鍵條件：機型、告警代碼、風機編號被省略，就會找到別的機型的手冊。提示要明確要求保留，並抽查改寫結果。
  • 話題已換還硬接：使用者從旋角改問偏航，改寫不該把旋角帶進來。提示要允許「無關就原句輸出」，也可同時檢索原句與改寫句再融合（第 010 堂的 RRF）。
  • 改寫時順便回答：改寫器只輸出問題。若它同時給答案，會讓後續流程拿到未經查證的內容。
  • 歷史越來越長：只取最近幾輪或先摘要舊歷史，否則改寫本身也會變慢變貴。
  • 單輪問答不需要：每個問題都獨立的系統（例如單次查告警代碼）不必多這一步，省下一次呼叫。
風場、機型、手冊與工單內容及數據皆為虛構，實際作業以原廠手冊與現場規範為準。互動範例的改寫句為事先寫好的模擬，不代表真實模型的輸出。

📝 小測驗

技師在第二輪只輸入「它要換哪個備品？」，系統直接拿這句去檢索卻失敗。最主要的原因是？

追問的指代與省略要靠對話歷史補完。先改寫成獨立問題，檢索系統才拿得到主題、機型與代碼。

對話式 RAG 中，檢索與生成兩個階段各自應該拿到什麼？

檢索要單句、資訊完整；生成要接得上話，所以仍需要對話歷史。
