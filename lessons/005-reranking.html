重排序：候選池抓對了，順序還可以更準

向量檢索（Bi-encoder）能從整本手冊裡快速抓出一批候選片段，但它把問題與文件各自壓成一個向量再比對，字詞之間的細微交互常常被平均掉，正確答案可能只排在候選池中間。重排序（Reranking）用更精細的 Cross-encoder 模型，把「問題」與「每一篇候選文件」綁在一起重新評分，只精排這一小批候選，換來更準確的排序。

🎬 動畫：候選池不變，順序變準了

🧩 重點整理

Bi-encoder 快但粗問題與文件各自獨立壓成一個向量，文件向量可以事先算好，一次比對就能從幾百萬篇裡抓出候選，但對字詞細節不夠敏感。
Cross-encoder 準但慢把問題與候選文件串成一對，一起送進同一個模型做 full attention 聯合計算，能捕捉字詞交互，但無法預先算好，只能逐篇對候選重新跑。
兩階段是業界標準做法先用 Bi-encoder 或混合檢索抓出候選池（通常幾十到幾百篇），再用 Cross-encoder 只對這一小批候選精排，兼顧速度與準度。
候選池大小是關鍵旋鈕Reranker 只能矯正候選池「裡面」的順序；候選池一開始就漏掉正解，重排也救不回來——這一點與上一堂的 RRF 融合完全相通。

🧪 互動範例：Bi-encoder 排序 vs. 重排後排序

下面是《OW-8 運維手冊》旋角系統章節的 13 個段落。由於這個網站是純靜態頁面、不載入外部機器學習函式庫，這裡的「Cross-encoder」是簡化模擬：把「Bi-encoder 相似度」與「問題和文件之間最長共同子字串的比例」加權合併，用來示意 Cross-encoder 能捕捉逐字對照、片語層級的關聯，而不是像 Bi-encoder 只比較兩個壓縮後的向量。切換模式，觀察哪些候選被重新排到前面、哪些被排到後面。

💻 程式範例（Python）

用 sentence-transformers 實作兩階段檢索：SentenceTransformer 做 Bi-encoder 召回，CrossEncoder 對候選池精排。正式環境也可以用 Cohere Rerank、Voyage Rerank 等托管重排序 API。

import numpy as np
from sentence_transformers import SentenceTransformer, CrossEncoder
import anthropic

# ① Bi-encoder 召回：文件向量事先算好，查詢來的時候只需再算一次
bi_encoder = SentenceTransformer("BAAI/bge-m3")
chunks = ["..."]  # 《OW-8 運維手冊》旋角系統各段落
chunk_vecs = bi_encoder.encode(chunks, normalize_embeddings=True)

def recall(question, top_n=20):
    q = bi_encoder.encode([question], normalize_embeddings=True)[0]
    scores = chunk_vecs @ q                       # 已正規化 → 內積即餘弦相似度
    top = np.argsort(-scores)[:top_n]
    return [chunks[i] for i in top]

# ② Cross-encoder 精排：問題與每篇候選一起送進模型，逐篇算一次聯合分數
reranker = CrossEncoder("BAAI/bge-reranker-v2-m3")

def rerank(question, candidates, top_k=3):
    pairs = [[question, c] for c in candidates]
    scores = reranker.predict(pairs)          # 無法預先算好，只能對候選逐篇跑
    order = np.argsort(-scores)[:top_k]
    return [candidates[i] for i in order]

def answer(question):
    candidates = recall(question, top_n=20)      # 候選池抓大一點
    top = rerank(question, candidates, top_k=3)   # reranker 只精排這一小批
    context = "\n".join(f"[{i+1}] {c}" for i, c in enumerate(top))
    prompt = ("只根據下列參考資料回答，並標註出處編號；資料中沒有就說不知道。\n\n"
              f"參考資料：\n{context}\n\n問題：{question}")
    client = anthropic.Anthropic()
    msg = client.messages.create(model="claude-sonnet-5", max_tokens=512,
                                 messages=[{"role": "user", "content": prompt}])
    return msg.content[0].text

print(answer("葉片旋角馬達故障怎麼處理？"))
# candidates 也可以先用上一堂的混合檢索（BM25 + 向量 + RRF）產生，reranker 只是最後再精排一次

⚖️ 三種做法比較

純 Bi-encoder（向量）純 Cross-encoder（對全庫重排）兩階段：Bi-encoder 召回 + Cross-encoder 精排
排序精準度中等：只比對壓縮後的向量最高：問題與文件聯合計算高：只精排候選池，仍保有 Cross-encoder 的精準度
查詢延遲低：一次 ANN 查詢極高：對全庫逐篇跑模型，規模一大就不可行中等：多一次對候選池的精排，但候選池通常只有幾十篇
可否預先算好文件向量✅ 可以，索引時就算好✗ 不行，問題與文件要一起輸入模型召回階段可以，精排階段不行
適用規模百萬篇級的整庫搜尋只適合幾十篇以內的小規模比較先用 Bi-encoder／混合檢索縮小到幾十篇，再精排
常見套件／服務FAISS、pgvector、Pinecone、Weaviatesentence-transformers CrossEncoderCohere Rerank、Voyage Rerank、BAAI bge-reranker 系列

⚠️ 重排序常見的坑 / 何時不該用

  • 候選池太小，重排也救不回來：如果 Bi-encoder 或混合檢索一開始只抓前 3 名就交給 Cross-encoder，正解不在候選池裡，重排師再精準也沒用——候選池要抓得比最終需要的 Top-k 大上許多。
  • 不要對整個資料庫直接跑 Cross-encoder：它沒辦法預先算好文件向量，也不能用 ANN 索引加速；沒有先用召回階段縮小規模，查詢延遲會大到無法接受。
  • 重排序模型的訓練資料要跟場景相符：許多公開的 Cross-encoder（例如以 MS MARCO 段落排序資料訓練）擅長的是「這段文字有沒有回答這個問題」，如果拿來判斷「這是不是最新版本的手冊」這類需求，效果可能不如預期，需要另外驗證或微調。
  • 重排序會增加延遲與成本：候選池裡每一篇都要多跑一次模型前向計算，線上服務要抓好延遲預算，候選池也不能無限增加。
  • 不是每個情境都值得多這一層：如果 Bi-encoder 或混合檢索本身準確度已經夠用（例如範圍小、結構化程度高的知識庫），多加一層 Cross-encoder 可能只有邊際改善，卻多了一份要維護與付費的服務。
範例中的鷗灣離岸風場、OW-8 機型、運維手冊內容、告警代碼與料號皆為虛構，僅供教學示範；互動範例中的「Cross-encoder」為簡化規則模擬，並非真正的深度學習模型；實際作業以原廠手冊與現場規範為準。

📝 小測驗

Cross-encoder 為什麼通常比 Bi-encoder 更能抓到問題與文件之間的細微關聯？

Bi-encoder 把問題與文件各自獨立編碼成一個向量，兩者在編碼過程中「沒有互相看過對方」，之後只用一次相似度比對；Cross-encoder 則是把問題與文件串接成一對，一起輸入同一個 Transformer，讓每個字詞都能互相注意，因此能捕捉到更細微的字詞交互，但也因此無法像 Bi-encoder 一樣預先算好文件向量。

下列關於「Bi-encoder 召回 + Cross-encoder 精排」兩階段檢索的敘述，何者最正確？

Cross-encoder 沒辦法預先算好文件向量，也不能用 ANN 索引加速，直接對整庫重排會讓查詢延遲大到無法接受；候選池也不能抓太少，否則正解一開始就被排除在外，重排也救不回來。業界常見做法是先用 Bi-encoder 或混合檢索抓出足夠大的候選池，再用 Cross-encoder 只精排這一小批。
