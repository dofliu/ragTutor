RAG 評估：忠實度、答案相關性、檢索召回

你把切塊大小從 500 字改成 300 字，換了嵌入模型，又改了提示詞，「感覺」答案變好了。但變好了多少？哪一題變差了？問題出在檢索還是生成？只靠試幾題沒有答案。RAG 評估先建一份有標準答案的評估集，再把系統拆成檢索與生成兩段分別打分：檢索看召回（該找的找到了嗎）與精確（找到的有用嗎），生成看忠實度（有沒有超出依據亂說）與答案相關性（有沒有答非所問）。

🎬 動畫：從「感覺不錯」到可量測

🧩 重點整理

先有評估集，再談好壞每題包含問題、應該被找到的段落與參考答案要點。固定的評估集讓每次調整都能公平比較，也能抓出「改好一題、弄壞三題」。
檢索與生成分開量召回看標準依據有沒有被找到，精確看取回的段落有多少有用；這兩項只需要標準依據，不需要 LLM 就能算。
忠實度與答案相關性看生成忠實度檢查答案的每個論述是否有取回段落作依據；答案相關性檢查答案是否回應問題。兩者通常要用 LLM 當評審。
指標是診斷，不是目的分數低的那一項指出該修哪一段；但評審模型會有偏差，要抽樣人工校對，並持續把線上的失敗案例補進評估集。

🧪 互動範例：調整檢索設定，看四個指標怎麼變

下面有 8 段虛構的《OW-8 運維手冊》內容與 4 題評估題，每題都標好「標準依據」（應該被找到的段落）與一份預先寫好的答案，答案已拆成幾個論述。這裡沒有真的 LLM 評審：召回與精確直接對照標準依據計算；忠實度用規則代替——某個論述若它所依據的段落有被取回就算「有依據」，沒有依據的論述（例如憑空冒出的工時）永遠算不到；答案相關性則是預先標好「有沒有答到問題」的論述比例。請切換檢索方式、調整取回數量 k，看分數如何變動，並讀最下方的診斷。

💻 程式範例（Python）

最小的評估流程：檢索指標直接用標準依據計算；忠實度請 LLM 逐一判斷「這個論述能否由段落推得」。用 anthropic SDK（pip install anthropic）。評估集、段落與問題皆為虛構；論述拆解在這裡寫死，實務上可再請 LLM 從答案中抽出。

import json, anthropic

client = anthropic.Anthropic()

# 1) 虛構評估集：問題 + 標準依據 + 這次系統的答案（已拆成論述）
EVAL_SET = [{
    "question": "HY-120 液壓壓力過低怎麼處理？",
    "gold_ids": ["hy120-steps", "hy120-safety"],      # 應該被找到的段落
    "retrieved": {                                 # 檢索系統這次取回的 Top-3
        "hy120-steps": "檢查油位與蓄壓器預充壓力；確認液壓泵運轉。",
        "hy121-temp": "HY-121 液壓油溫過高：檢查散熱器。",
        "yw042": "YW-042 偏航誤差過大：校正風向感測器。",
    },
    "claims": ["先檢查油位與蓄壓器預充壓力", "確認液壓泵運轉", "更換蓄壓器約需 2 小時"],
}]

# 2) 檢索指標：不需要 LLM
def recall(retrieved_ids, gold_ids):
    return len(set(retrieved_ids) & set(gold_ids)) / len(gold_ids)

def precision(retrieved_ids, gold_ids):
    return len(set(retrieved_ids) & set(gold_ids)) / len(retrieved_ids)

# 3) 忠實度：LLM 當評審，逐一判斷論述是否能由段落推得
def is_supported(claim, context):
    resp = client.messages.create(
        model="claude-sonnet-5", max_tokens=20,
        messages=[{"role": "user", "content":
            f"段落：\n{context}\n\n論述：{claim}\n"
            "只根據段落判斷，論述是否能被段落支持？只回答 yes 或 no。"}])
    return resp.content[0].text.strip().lower().startswith("yes")

def faithfulness(claims, context):
    return sum(is_supported(c, context) for c in claims) / len(claims)

# 4) 跑整份評估集，輸出平均分數
rows = []
for item in EVAL_SET:
    ids = list(item["retrieved"])
    context = "\n".join(item["retrieved"].values())
    rows.append({"recall": recall(ids, item["gold_ids"]),
                 "precision": precision(ids, item["gold_ids"]),
                 "faithfulness": faithfulness(item["claims"], context)})
for m in rows[0]:
    print(m, round(sum(r[m] for r in rows) / len(rows), 2))

答案相關性的做法類似：請評審判斷「答案有沒有回應問題」，或像 Ragas 論文那樣，讓 LLM 從答案反推可能的問題，再與原問題比較相似度。實務上建議把評審的提示詞固定下來，並抽樣與人工判斷對照，確認評審沒有系統性偏差。

適合用在剛起步的快速確認調切塊、嵌入、重排序（第 002～005 堂）時的每次迴歸測試調提示詞、壓縮、Self-RAG（第 012～013 堂）等影響生成的改動建立評估集、校準評審、處理高風險題目

實務上會混用：評估集用人工建立，檢索指標每次改動都跑，LLM 評審跑在同一份評估集上，再定期抽樣人工複核評審的結果。

⚠️ RAG 評估常見的坑 / 何時不該用

  • 評估集太小或太簡單：只有十幾題簡單題，分數永遠漂亮。要涵蓋常見題、難題、查不到的題目（正確回答應是「手冊沒寫」），並把線上的失敗案例補進去。
  • 只看平均分數：平均 90% 可能藏著一類題目全軍覆沒。要依題型（告警代碼、安全規範、備品）分組看，並檢視最差的幾題。
  • 把評審模型當真理：LLM 評審可能偏好較長的答案或較早出現的選項，也會被措辭誤導（見 Zheng 等人對 LLM-as-a-judge 偏差的討論）。要抽樣與人工判斷對照，評審提示詞固定後才能比較。
  • 標準依據不只一份：同一個答案可能散在多段，或不同段落都能回答。標註時要容許多個可接受的依據，不然召回會被低估。
  • 為指標而優化：反覆針對同一份評估集調整，會過度貼合它。要留一份不看的測試題，定期更新。
  • 忠實不等於正確：答案若忠實引用了「過期的手冊」，忠實度仍是滿分。資料版本管理與來源品質要另外把關。
  • 安全關鍵內容不能只靠分數：高處作業、上鎖掛牌這類題目，要有專家逐題審查，不能因為平均分數高就放行。
  • 沒有評估集就不必急著上複雜流程：連基本的召回都沒量過，就不要先導入更複雜的技術；先量出瓶頸在哪一段。
風場、機型、手冊內容與數據皆為虛構，實際作業以原廠手冊與現場規範為準。互動範例的段落、標準依據、論述與分數皆為虛構示範，忠實度以規則模擬而非真正的 LLM 評審，不可作為實際維修決策依據。

延伸閱讀：Es 等，〈RAGAS: Automated Evaluation of Retrieval Augmented Generation〉（arXiv:2309.15217，提出免參考答案的忠實度、答案相關性與上下文相關性等指標）；Saad-Falcon 等，〈ARES: An Automated Evaluation Framework for Retrieval-Augmented Generation Systems〉（arXiv:2311.09476）；Zheng 等，〈Judging LLM-as-a-Judge with MT-Bench and Chatbot Arena〉（arXiv:2306.05685）。各評估框架對指標的定義與所需欄位會隨版本調整，使用前請查閱當前文件。

📝 小測驗

評估集的標準依據有 2 段，系統取回 4 段，其中只有 1 段是標準依據。召回與精確各是多少？

召回 ＝ 命中的標準依據 ÷ 標準依據總數 ＝ 1/2；精確 ＝ 命中的段落 ÷ 取回的段落 ＝ 1/4。

檢索召回 100%，但答案裡有一句「更換約需 2 小時」在取回的段落中找不到。哪個指標最先反映問題？該先檢查哪一段？

該找的都找到了，檢索沒問題；多出來的論述沒有依據，是模型自己補的，屬於忠實度問題，應從生成端的提示詞與約束著手。
