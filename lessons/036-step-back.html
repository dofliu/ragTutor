Step-Back 後退一步提問：先問上位問題，再找證據

技師問「WTG-17 在 38°C 下 PT-203 連續復歸 3 次，可以繼續運轉嗎？」問句塞滿機號、溫度與次數，檢索被這些細節拉去撈現場日誌，反而漏掉「旋角馬達過溫的一般原因與處置原則」。Step-Back（後退一步）先請模型把具體問題抽象成上位問題，用它找出一般原則，再和原問題那一路的結果合併，讓模型能依原則推理具體情況。

🎬 動畫：先退一步，再往前走

🧩 重點整理

先抽象再檢索Step-Back Prompting 的核心是兩步：先抽象出上位概念與原則，再依原則推理。用在 RAG，就是多產生一句後退問題去檢索。
兩路合併，不取代原問題後退問題找一般原則，原問題找精確的規則與紀錄。兩路用 RRF 融合，才不會丟掉機號、告警代碼這類精確資訊。
退多遠要拿捏只拿掉機號、數值、次數等細節，保留子系統與故障類型。退得太遠會變成空泛的大話，擠掉真正相關的段落。
不是每題都需要單純查告警代碼或料號，直接檢索即可；問題夾帶多個細節、答案要靠原則推理時才有價值。多一次模型呼叫與一路檢索，要先評估再上線。

🧪 互動範例：只用原問題 vs 原問題＋後退問題

知識庫是 12 段虛構的《OW-8 運維手冊》與輔助文件。每個預設問題都附一句預先寫好的後退問題（模擬模型的輸出，真實系統由模型生成）。檢索是瀏覽器內真的在算（BM25，中文用二字詞）。請比較三種做法：只用原問題、只用後退問題、兩路用 RRF 合併；第三個預設問題是不需要後退的簡單題。也可以切換成「退太遠」的後退問題，看看會發生什麼事。

A. 只用原問題
B. 只用後退問題
C. 兩路合併（RRF）

💻 程式範例（Python）

下面是最小實作：用 claude-sonnet-5 產生後退問題，原問題與後退問題各檢索一次，再用 RRF 合併。範例以空白斷詞，中文實務上請換成適合的斷詞器。

import anthropic
from rank_bm25 import BM25Okapi

client = anthropic.Anthropic()

DOCS = [
    "旋角馬達過溫的一般原因：冷卻風扇故障、散熱片積塵、負載電流偏高、環境溫度偏高。",
    "告警復歸規則：同一告警短時間連續復歸 3 次，須停機檢查，不得繼續運轉。",
    "WTG-17 運轉日誌：環境溫度 38°C，PT-203 告警連續 3 次復歸後繼續運轉。",
]
bm25 = BM25Okapi([d.split() for d in DOCS])

def step_back(question):
    prompt = ("請把下列問題改寫成較抽象的上位問題：拿掉機號、數值與次數，"
              "但保留子系統與故障類型。只輸出一句問題。\n\n問題：" + question)
    msg = client.messages.create(model="claude-sonnet-5", max_tokens=100,
                                 messages=[{"role": "user", "content": prompt}])
    return msg.content[0].text.strip()

def rank(query):
    scores = bm25.get_scores(query.split())
    return sorted(range(len(DOCS)), key=lambda i: -scores[i])

def rrf(rankings, k=60):
    score = {}
    for r in rankings:
        for pos, i in enumerate(r):
            score[i] = score.get(i, 0) + 1 / (k + pos + 1)
    return sorted(score, key=score.get, reverse=True)

q = "WTG-17 在 38°C 下 PT-203 連續復歸 3 次，可以繼續運轉嗎？"
sb = step_back(q)                       # 例如：旋角馬達過溫的一般原因與處置原則
top = rrf([rank(q), rank(sb)])[:3]    # 兩路合併，保留原問題那一路
for i in top:
    print(DOCS[i])

實務上，後退問題的提示要限定「同一子系統與故障類型」；上線前用評估集比較「只用原問題」與「原問題＋後退」的召回，再決定是否值得多一次呼叫。

⚠️ Step-Back 常見的坑 / 何時不該用

  • 退得太遠：「風機故障怎麼處理」會撈到各子系統的概論。提示要限定保留子系統與故障類型，只拿掉機號、數值與次數。
  • 丟掉原問題：告警代碼、機號、工單號是精確資訊，只用後退問題會漏掉。務必保留原問題那一路再融合。
  • 簡單題也後退：單純查「PT-205 怎麼排除」，後退只會多花一次呼叫並引入雜訊。可先做簡單的路由判斷（第 015 堂 Adaptive RAG）。
  • 後退問題本身出錯：模型可能抽象錯方向（把過溫抽象成煞車）。上線前抽樣檢查，並記錄每次的後退問題以便除錯。
  • 成本與延遲：多一次模型呼叫與一路檢索。要用自己的評估集量測效益，不要照搬別人的數字。
  • 原則不等於答案：後退找到的是一般原則，具體能不能繼續運轉仍要依現場規定與工程師判斷。
風場、機型、手冊內容、告警代碼與數據皆為虛構，實際作業以原廠手冊與現場規範為準。互動範例的後退問題是預寫腳本，不是真實的模型輸出。

📝 小測驗

在 RAG 中使用 Step-Back，後退問題通常和原問題怎麼搭配？

原問題保留機號、代碼等精確資訊，後退問題補上一般原則，兩路合併才互補。

下列哪一種後退問題「退得太遠」？

後退要保留子系統與故障類型；「風機故障」太空泛，會撈到各子系統的概論。
