第 011 堂進階約 12 分鐘

中繼資料過濾與自我查詢檢索

技師問「OW-6 的旋角系統保養週期」，知識庫裡同時有 OW-8 與 OW-6 兩版手冊，兩版的保養段落字面幾乎一樣，向量檢索只看主題相似度，前幾名全是 OW-8 的內容，答案就會講錯版本。中繼資料過濾（Metadata Filtering）在建索引時替每個段落存下機型、子系統、文件類型等結構化欄位；自我查詢檢索（Self-Query）則讓 LLM 把問題拆成「語意查詢 + 過濾條件」，先縮小範圍再做向量檢索。

🎬 動畫：把問題拆成「要找什麼」與「限定哪一類」

🧩 重點整理

條件不該交給向量猜機型、子系統、文件類型、日期是明確的條件，用精確比對比用語意相似度可靠。向量負責「像不像」，過濾負責「是不是」。
欄位要在建索引時存好每個段落除了文字與向量，還要附上結構化中繼資料。欄位值要正規化；缺欄位的段落在過濾時會被排除或漏掉。
Self-Query：讓 LLM 拆問題給 LLM 欄位清單與可用值，請它輸出「語意查詢 + 過濾條件」的結構化結果，程式再拿去呼叫向量資料庫。使用者不必自己填表單。
先過濾比後過濾穩先檢索 Top-K 再過濾，條件嚴格時可能一筆不剩。能在檢索時就帶條件（pre-filter）通常較好，實際支援程度依向量資料庫而異。

🧪 互動範例：不過濾 vs. 後過濾 vs. 前過濾

下面是虛構的《OW-8 運維手冊》《OW-6 運維手冊》、技術通報與工單共 11 個段落，每個段落都有機型、子系統、文件類型三個欄位。輸入問題（或點範例），程式用簡單規則模擬 Self-Query 解析（真實系統是由 LLM 完成），抽出語意查詢與過濾條件。接著切換三種做法，並調整後過濾先取的候選數 K。也可以取消勾選某個條件，或模擬「LLM 把機型解析錯」，看看過濾的風險。檢索用簡化的 TF-IDF 餘弦相似度模擬，不是真正的嵌入模型。

💻 程式範例（Python）

手動實作 Self-Query：每個段落帶中繼資料；用 claude-sonnet-5 把問題拆成語意查詢與過濾條件（並用欄位白名單驗證 LLM 的輸出）；先用遮罩過濾，再在符合條件的段落裡做向量檢索。範例文件為虛構。

import json
import numpy as np
from sentence_transformers import SentenceTransformer
import anthropic

client = anthropic.Anthropic()
embedder = SentenceTransformer("BAAI/bge-m3")

# ① 知識庫：每個段落附上中繼資料（虛構的 OW-8 / OW-6 手冊）
docs = [
    {"text": "旋角系統定期保養：每 12 個月檢查旋角軸承潤滑、馬達碳刷與編碼器接線。",
     "model": "OW-8", "system": "旋角", "doc_type": "手冊"},
    {"text": "旋角軸承潤滑與馬達碳刷檢查：每 6 個月執行一次，並記錄潤滑脂用量。",
     "model": "OW-6", "system": "旋角", "doc_type": "手冊"},
    {"text": "技術通報 TB-2026-07：旋角軸承潤滑脂在高濕環境劣化較快，檢查間隔縮短為每 4 個月。",
     "model": "OW-6", "system": "旋角", "doc_type": "技術通報"},
    # ……
]
vecs = embedder.encode([d["text"] for d in docs], normalize_embeddings=True)

# ② Self-Query：LLM 只能用這些欄位與值
ALLOWED = {
    "model": ["OW-8", "OW-6"],
    "system": ["旋角", "偏航", "齒輪箱"],
    "doc_type": ["手冊", "技術通報", "工單"],
}

def parse_query(question):
    msg = client.messages.create(
        model="claude-sonnet-5", max_tokens=300,
        messages=[{"role": "user", "content":
            "把風機運維問題拆成 JSON：{\"query\": 語意查詢, \"filter\": {欄位: 值}}。\n"
            "filter 只能使用下列欄位與值；問題沒提到的欄位不要猜；只輸出 JSON。\n"
            + json.dumps(ALLOWED, ensure_ascii=False) + "\n問題：" + question}])
    data = json.loads(msg.content[0].text)
    # LLM 的輸出不可盡信：用白名單檢查欄位與值
    filt = {k: v for k, v in data.get("filter", {}).items()
            if v in ALLOWED.get(k, [])}
    return data["query"], filt

# ③ 先過濾（遮罩），再在符合條件的段落裡做向量檢索
def search(question, top_n=3):
    query, filt = parse_query(question)
    mask = np.array([all(d[k] == v for k, v in filt.items()) for d in docs])
    if not mask.any():
        return []                      # 條件太嚴：可改成放寬條件再查一次
    q = embedder.encode([query], normalize_embeddings=True)[0]
    scores = np.where(mask, vecs @ q, -np.inf)    # 不符合條件的直接排除
    order = np.argsort(-scores)[:min(top_n, int(mask.sum()))]
    return [docs[i] for i in order]

for d in search("OW-6 的旋角系統保養週期"):
    print(d["model"], d["doc_type"], d["text"], "\n---")

⚖️ 三種做法比較

一般檢索（第 001 堂）情境化檢索（第 009 堂）中繼資料過濾（本堂）
解決什麼問題找出語意相近的段落段落脫離文件脈絡，彼此難分辨同主題但不同機型、文件類型或日期的段落混在一起
脈絡放在哪不處理由 LLM 寫成文字，併進段落一起嵌入存成結構化欄位，查詢時精確比對
額外成本無索引階段每個段落一次 LLM 呼叫建索引時補欄位；每次查詢多一次 LLM 解析
主要風險同主題的不同版本分不開索引成本高；寫入的脈絡可能不準條件解析錯誤或欄位缺漏，會把正解直接濾掉

兩者可以疊加：用中繼資料縮小範圍，範圍內再用混合檢索（第 004 堂）與重排序（第 005 堂）。情境化檢索解決「文字缺脈絡」，中繼資料過濾解決「條件要精確」，彼此互補。

⚠️ 中繼資料過濾常見的坑 / 何時不該用

  • LLM 解析錯，正解被直接濾掉：互動範例勾選「模擬 LLM 解析錯誤」就能看到，機型被寫反後，Top-N 裡一個正確段落都沒有，而且看起來還很整齊。要用欄位白名單驗證輸出、記錄解析結果，並在結果為 0 筆時放寬條件重試。
  • 過度過濾：把文件類型限定為「手冊」，就會漏掉後來發布、內容更新的技術通報。問題沒有明確要求的欄位，不要替使用者猜。
  • 問題沒提機型怎麼辦：互動範例的「偏航系統的保養週期」沒有機型，兩版手冊都會出現。可以不過濾並在答案標明版本，或由系統反問「是哪一款機型？」，不要預設其中一款。
  • 欄位值不一致：段落標成「OW8」、問題寫「OW-8」，精確比對就對不上。入庫時統一格式，並讓 LLM 只能從允許值清單挑選。
  • 過濾不是排序：條件只決定留不留，留下來的段落仍要靠檢索排序。符合條件的段落若很多，仍需要好的檢索與重排序。
  • 權限不能只靠 LLM 解析：像「只能看自己風場的工單」這類存取控制，必須由系統在程式端強制加上條件，不能依賴 LLM 從問題中產生，更不能讓使用者用問法繞過。
  • 資料不大或沒有明確欄位就不必做：知識庫只有單一機型、單一文件類型時，過濾沒有可以限定的東西，多一次 LLM 解析只是白花成本。
範例中的鷗灣離岸風場、OW-8 / OW-6 機型、運維手冊與技術通報內容、工單與各項保養週期皆為虛構，僅供教學示範；互動範例的 Self-Query 解析為簡化規則、檢索為簡化的 TF-IDF 模擬；實際作業以原廠手冊與現場規範為準。

📝 小測驗

技師問「OW-6 的旋角系統保養週期」，為什麼只靠向量相似度可能找到 OW-8 的段落？

嵌入向量表達的是語意相近程度；機型常寫在檔案屬性而不在段落文字裡，兩版段落的向量就幾乎一樣。要精確限定機型，應該把它存成中繼資料，查詢時用條件過濾。

「後過濾」（先取 Top-K 再過濾）相較於「前過濾」（先過濾再檢索）最主要的風險是什麼？

後過濾是在已取出的 K 筆候選裡丟掉不符合的。條件越嚴格、符合的段落排名越後面，剩下的越少。前過濾在檢索時就只考慮符合條件的段落，可以取滿 N 筆（前提是符合的段落夠多）。
