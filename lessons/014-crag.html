CRAG 修正式 RAG：檢索品質評估與網路補救

檢索器不是每次都對。技師問「OW-8 的 PT-211 怎麼處理」，手冊裡可能只有舊款 OW-6 的角度偏差段落，字面很像、內容卻不適用，一般 RAG 仍照單全收。CRAG（Corrective Retrieval-Augmented Generation，修正式 RAG）在檢索與生成之間加一個輕量的檢索評估器，替每份文件打信心分數，再判成「正確、錯誤、模糊」三種情況：正確就精煉後使用，錯誤就丟掉並改用其他來源補救，模糊就兩邊合併。

🎬 動畫：先評估檢索結果，再決定怎麼用

🧩 重點整理

多一個評估器CRAG（Yan 等人，2024）在檢索與生成之間放一個輕量的檢索評估器，替每份文件評估與問題的相關程度，不需要動到檢索器或生成模型。
三種動作依信心分數分成正確（Correct）、錯誤（Incorrect）、模糊（Ambiguous）：正確就精煉文件，錯誤就丟棄並補救檢索，模糊則兩種結果一起用。
補救檢索與知識精煉原論文以網頁搜尋補救，並把文件拆成小片段、濾掉無關的再重組（decompose-then-recompose）。風場可把補救來源換成技術通報庫或原廠公開文件。
即插即用，但評估器要可信CRAG 可套在各種 RAG 流程上；整個系統的上限取決於評估器的準確度，門檻太鬆放壞資料進來，太嚴則常常白白去補救。

🧪 互動範例：一般 RAG vs CRAG

下面用虛構文件模擬三種問題。檢索是真的在瀏覽器裡算（簡化的 TF-IDF 餘弦相似度，取前 3 名）；補救檢索也是真的對「技術通報庫」另建索引，用改寫後的關鍵字去查；知識精煉真的把文件切成句子，只留下與問題有重疊詞元的片段。但評估器的信心分數無法在網頁內由真的微調模型產生，這裡以人工標註的分數模擬，真實評估器會有誤差。切換「一般 RAG」與「CRAG」，再調整門檻，看看判斷怎麼改變。

💻 程式範例（Python）

原論文的評估器是另外微調的小模型，補救檢索用網頁搜尋。這裡用 claude-sonnet-5 以提示詞當評估器，做「CRAG 風格」的近似：逐份打分、依門檻判斷動作、錯誤時改寫查詢查通報庫、最後把文件切成句子只留相關的。範例文件為虛構，retrieve 與 search_bulletins 請換成你自己的檢索器。

import json
import re
import anthropic

client = anthropic.Anthropic()
MODEL = "claude-sonnet-5"
UPPER, LOWER = 0.7, 0.3   # 上、下門檻：請用自己的評估集調整

def ask(prompt, max_tokens=300):
    msg = client.messages.create(model=MODEL, max_tokens=max_tokens,
        messages=[{"role": "user", "content": prompt}])
    return msg.content[0].text

# 假設的檢索器：回傳 [{"id": "...", "text": "..."}]
def retrieve(question, k=3): ...          # 查《OW-8 運維手冊》
def search_bulletins(keywords, k=2): ...   # 查技術通報庫（取代原論文的網頁搜尋）

def score(question, text):
    # 評估器：這份文件能回答問題嗎？機型與告警代碼必須相符
    out = ask(f'問題：{question}\n文件：{text}\n'
              '這份文件能回答問題嗎（機型與告警代碼需相符）？只輸出 0 到 1 的數字。')
    return float(re.search(r"[01](?:\.\d+)?", out).group())

def refine(question, text):
    # 知識精煉：切成句子，逐句評分，只留下相關的再重組
    strips = [s for s in text.split("。") if s.strip()]
    return "。".join(s for s in strips if score(question, s) >= LOWER)

def crag(question):
    docs = retrieve(question)
    scores = [score(question, d["text"]) for d in docs]

    if max(scores) >= UPPER:                 # Correct
        action = "correct"
    elif max(scores) < LOWER:                # Incorrect
        action = "incorrect"
    else:                                  # Ambiguous
        action = "ambiguous"

    context = []
    if action in ("correct", "ambiguous"):
        context += [(d["id"], refine(question, d["text"]))
                    for d, s in zip(docs, scores) if s >= LOWER]
    if action in ("incorrect", "ambiguous"):
        # 補救：把問題改寫成關鍵字，改查其他來源
        kw = ask(f'把問題改寫成 3～6 個搜尋關鍵字，空白分隔，只輸出關鍵字：{question}')
        context += [(d["id"], refine(question, d["text"])) for d in search_bulletins(kw)]

    if not context:
        return "手冊與通報中查無足夠依據，建議詢問原廠。"
    refs = "\n".join(f"[{i}] {t}" for i, t in context)
    return ask(f"只根據下列資料回答，並標註來源編號。\n{refs}\n問題：{question}", 400)

print(crag("OW-8 的 PT-211 葉片角度偏差過大怎麼處理"))

每份文件多一次評分呼叫，精煉時每個句子又多一次，成本不低；實務上可以改用小型分類模型當評估器，或只對信心分數落在模糊區間的文件做精煉。

⚠️ CRAG 常見的坑 / 何時不該用

  • 評估器會判錯：把舊款 OW-6 的段落判成高分，壞資料就直接通關；把好文件判成低分，又會白白丟棄。要用評估集量測，不要憑感覺調門檻。
  • 門檻太鬆或太嚴都有代價：互動範例中，上門檻降到 0.5，原本需要補充的「模糊」題會被判為正確，漏掉通報裡的新資訊；下門檻升高，則更常放棄手冊轉去補救。
  • 補救來源本身要可信：原論文用網頁搜尋，網路內容良莠不齊；在運維場景，建議補救來源限定為通報庫、原廠公開文件等受控資料，不要直接開放全網。
  • 機密與資安：把工單或設備代碼放進外部搜尋的查詢，可能洩漏內部資訊。改寫查詢時要先去識別化，或只查內部來源。
  • 精煉可能切掉關鍵前提：把安全注意事項（例如先鎖定葉輪、LOTO）當成不相關而濾掉，後果比答不出來更嚴重。高風險段落可設成「一律保留」。
  • 延遲與費用：每份文件多一次評估，補救時又多一輪檢索。檢索品質本來就穩定、問題簡單時，固定流程加重排序通常更划算。
風場、機型、手冊內容與數據皆為虛構，實際作業以原廠手冊與現場規範為準。互動範例的檢索為簡化的 TF-IDF 模擬，評估器信心分數以人工標註模擬；範例中的告警代碼、通報編號與步驟僅供教學示範。

延伸閱讀：Yan、Gu、Zhu、Ling，〈Corrective Retrieval Augmented Generation〉（arXiv:2401.15884）。

📝 小測驗

CRAG 的評估器判定「所有檢索到的文件都不可靠」（Incorrect）時，會怎麼做？

Incorrect 代表檢索結果整體不可信，所以丟棄；原論文改用網頁搜尋補救。只調大 top-k 通常撈到更多同類的壞文件。

評估器的信心分數落在上、下門檻之間（Ambiguous）時，最合理的處理是？

模糊代表把握不大，既不能完全相信原文件，也不該全部丟棄，所以兩邊合併，讓互補的資訊一起進來；代價是多一次補救檢索。
