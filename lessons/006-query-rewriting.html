查詢改寫與多重查詢：一個模糊問題，展開成好幾個精確查詢

使用者的問題常常很模糊、口語化，或者背後其實對應好幾種不同的原因，但手冊裡的段落用的是精確的技術詞彙。查詢改寫（Query Rewriting）先讓 LLM 讀懂意圖、換成手冊慣用的說法；多重查詢（Multi-Query）則更進一步，把一個問題展開成好幾個不同角度的查詢，各自檢索後再合併，涵蓋單一查詢用詞找不到的段落。

🎬 動畫：從一句模糊的話，到涵蓋多種原因的診斷

🧩 重點整理

問題不只一種原因模糊、口語化的問題背後常對應好幾個不同子系統，只送一次原始查詢等於只賭一種可能，命中率全憑運氣。
先寫，再查，再讀Rewrite-Retrieve-Read 框架讓 LLM 先把問題改寫成手冊慣用的技術詞彙，取代直接把使用者的原句拿去檢索。
多重查詢展開涵蓋面Multi-Query 讓 LLM 生成好幾個不同角度的查詢，各自獨立檢索，涵蓋單一查詢用詞永遠找不到的段落。
聯集只是起點合併去重後的候選清單還沒有跨查詢的統一排序；後續的「RAG-Fusion」會改用 RRF（倒數排名融合）取代單純聯集，排序更有依據。

🧪 互動範例：單一查詢 vs. 查詢改寫 + 多重查詢

下面是《OW-8 運維手冊》裡與「跳機／保護性停機」相關的 12 個段落，涵蓋變流器、電網保護、齒輪箱、主軸承、安全鏈等好幾個不同子系統。選一句值班人員常見的口語回報，切換「單一原始查詢」與「查詢改寫＋多重查詢」，比較兩種做法各自檢索到的段落——這裡的「改寫」是預先寫好的示範查詢，模擬 LLM 會生成的結果，因為本網站不會呼叫真正的語言模型。

💻 程式範例（Python）

用 anthropic SDK 讓 LLM 把值班人員的口語問題展開成多個改寫查詢，各自用 sentence-transformers 做向量檢索，再對結果聯集去重（同一片段保留最高分）。

import numpy as np
from sentence_transformers import SentenceTransformer
import anthropic

# ① 索引階段：跳機／保護性停機相關段落先算好向量
embedder = SentenceTransformer("BAAI/bge-m3")
chunks = ["..."]  # 《OW-8 運維手冊》各子系統的跳機／保護動作段落
chunk_vecs = embedder.encode(chunks, normalize_embeddings=True)
client = anthropic.Anthropic()

# ② 查詢改寫 + 多重查詢：把口語問題展開成 N 個精確角度
def rewrite_queries(question, n=4):
    prompt = (f"值班人員回報的問題：「{question}」\n"
              f"請改寫成 {n} 個更精確、涵蓋不同可能子系統原因的檢索查詢，"
              "只能使用風機運維手冊常見的技術詞彙，每行一個查詢，不要加編號。")
    msg = client.messages.create(model="claude-sonnet-5", max_tokens=200,
                                 messages=[{"role": "user", "content": prompt}])
    return [q.strip() for q in msg.content[0].text.split("\n") if q.strip()]

def retrieve(query, top_n=3):
    q = embedder.encode([query], normalize_embeddings=True)[0]
    scores = chunk_vecs @ q                        # 已正規化 → 內積即餘弦相似度
    top = np.argsort(-scores)[:top_n]
    return [(chunks[i], scores[i]) for i in top]

def multi_query_retrieve(question, top_n=3):
    merged = {}  # chunk -> 最高分數（聯集去重）
    for q in rewrite_queries(question):
        for chunk, score in retrieve(q, top_n):
            if chunk not in merged or score > merged[chunk]:
                merged[chunk] = score
    return sorted(merged.items(), key=lambda x: -x[1])

def answer(question):
    hits = multi_query_retrieve(question)
    context = "\n".join(f"[{i+1}] {c}" for i, (c, _) in enumerate(hits))
    prompt = (f"參考資料：\n{context}\n\n問題：{question}\n"
              "請列出可能原因與對應排除步驟；資料中沒有就說不知道。")
    msg = client.messages.create(model="claude-sonnet-5", max_tokens=512,
                                 messages=[{"role": "user", "content": prompt}])
    return msg.content[0].text

print(answer("風機一直自己停機"))

⚖️ 四種做法比較

原始查詢直接檢索單一查詢改寫（Rewrite）多重查詢 Multi-Query（本堂）RAG-Fusion（後續課程）
檢索次數1 次1 次改寫 + 1 次檢索1 次改寫 + N 次檢索1 次改寫 + N 次檢索
結果合併方式不需要不需要（仍是一組結果）聯集去重，取最高分倒數排名融合（RRF），依名次加權
適合情境問題本身已經很精確，例如直接輸入告警代碼問題意圖單一，只是措辭模糊或口語化問題背後可能有好幾種不同原因，需要涵蓋面多查詢結果需要一個更有依據的整體排序
主要缺點模糊、口語化的問題常常找不到如果背後其實有多種原因，仍只挑一種角度檢索次數隨 N 增加；聯集後缺乏跨查詢的排序權重多一個融合參數（RRF 的 k 值）需要調整

⚠️ 查詢改寫與多重查詢常見的坑 / 何時不該用

  • 已經很精確的查詢不需要改寫：像直接輸入「PT-203」這種告警代碼，語意已經非常明確，改寫或展開成多個查詢只會增加延遲與成本，效果有限。
  • 改寫本身可能出錯：如果 LLM 改寫時自己編造了手冊裡沒有的告警代碼或子系統名稱，反而會讓檢索走偏；提示詞裡最好限制只能使用已知的技術詞彙，或事後檢查改寫結果是否合理。
  • 查詢數量與成本的取捨：每多一個改寫查詢，就多一次向量運算與檢索，數量沒有上限地增加會拖慢回應時間、增加向量資料庫負載；實務上通常抓 3～5 個就足夠。
  • 聯集不是排序：這堂課的合併方式只是「去重後全部列出」，不同子查詢命中的片段彼此之間還沒有一個統一、可比較的分數；需要更精準的整體排序時，還要再加一層重排序，或改用 RAG-Fusion 的 RRF 融合。
  • 救不了檢索品質本身的問題：如果向量索引的嵌入模型或切塊策略本來就很差，再多改寫查詢也救不回離題的結果——查詢改寫解決的是「問題怎麼問」，不是「資料庫找不找得到」。
範例中的鷗灣離岸風場、OW-8 機型、運維手冊內容、告警代碼與料號皆為虛構，僅供教學示範；互動範例中的「改寫查詢」為預先寫好的示範文字，並非真正呼叫語言模型產生；實際作業以原廠手冊與現場規範為準。

📝 小測驗

為什麼要把一個模糊問題展開成「多個」改寫查詢，而不是只改寫成一句更精確的查詢？

像「風機一直自己停機」這樣的問題，背後可能是變流器過溫、電網保護動作、齒輪箱溫度過高、旋角備援電源異常等好幾種不同原因。只改寫成一句更精確的查詢，仍然只能挑中其中一個角度；用多重查詢展開成好幾個不同角度的查詢、各自獨立檢索，才能涵蓋更多可能的原因。

關於查詢改寫與多重查詢，下列敘述何者正確？

每多一個改寫查詢就多一次向量運算與檢索，數量沒有上限地增加會拖慢回應時間、增加成本，實務上通常抓 3～5 個就足夠；聯集去重後的結果也還沒有跨查詢的統一排序，需要更精準時還要再加一層重排序或改用 RRF 融合；而語意已經很明確的查詢（如告警代碼）再展開成多個查詢，效益有限卻多花成本。
