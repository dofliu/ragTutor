Self-RAG：模型自己判斷何時檢索、是否可信

一般 RAG 是固定流程：每個問題都檢索、檢索到什麼就全塞給模型。技師問「旋角系統是做什麼用的」其實不必查手冊；問「PT-203 怎麼處理」卻可能撈到舊款 OW-6 的段落，模型照單全收。Self-RAG（Self-Reflective RAG）訓練模型在生成時順便輸出特殊的反思詞元（reflection tokens），自己決定「要不要檢索」、「這段相關嗎」、「我寫的句子有依據嗎」，最後只採用有依據的內容。

🎬 動畫：讓模型自己當檢查員

🧩 重點整理

檢索變成「按需」模型先輸出 [Retrieve]（Yes／No／Continue）。不需要查手冊的問題直接回答，省下檢索與長上下文的成本。
三種批判詞元[IsRel] 段落是否相關、[IsSup] 句子被段落支持到什麼程度（完全／部分／無）、[IsUse] 整體回答是否有用（1–5 分）。
推論時可調行為論文在解碼時以分段束搜尋（segment-level beam search），用批判詞元機率加權選片段；調權重或檢索門檻，就能偏向「更嚴謹」或「更完整」，不必重新訓練。
代價在訓練原始做法要先訓練批判模型標註資料，再微調生成模型。若只想要類似效果，常見的折衷是用提示詞讓 LLM 當裁判（近似做法，不等於原論文）。

💻 程式範例（Python）

原論文需要微調出會輸出反思詞元的模型；一般 API 無法輸出這些詞元，所以這裡用 claude-sonnet-5 以提示詞做「Self-RAG 風格」的近似：先判斷要不要檢索，再逐段判斷相關性，生成後檢查是否被段落支持，最後只採用有依據的草稿。範例文件為虛構，函式 retrieve 請換成你自己的檢索器。

import json
import anthropic

client = anthropic.Anthropic()
MODEL = "claude-sonnet-5"

def ask_json(prompt, max_tokens=300):
    msg = client.messages.create(model=MODEL, max_tokens=max_tokens,
        messages=[{"role": "user", "content": prompt + "\n只輸出 JSON，不要其他文字。"}])
    return json.loads(msg.content[0].text)

# 假設的檢索器：回傳 [{"id": "...", "text": "..."}]，例如虛構的 OW-8 運維手冊、工單、通報
def retrieve(question, k=3): ...

def self_rag(question):
    # ① [Retrieve]：需要查手冊嗎？（問告警代碼、料號、步驟 → yes；問一般概念 → no）
    need = ask_json(f'問題：{question}\n這題需要查《OW-8 運維手冊》或工單才能可靠回答嗎？'
                    '輸出 {"retrieve": true 或 false}')["retrieve"]
    if not need:
        return client.messages.create(model=MODEL, max_tokens=400,
            messages=[{"role": "user", "content": question}]).content[0].text

    kept = []
    for p in retrieve(question):
        # ② [IsRel]：段落和問題相關嗎？（機型、告警代碼要對得上）
        rel = ask_json(f'問題：{question}\n段落：{p["text"]}\n'
                       '這段是否可用來回答問題（機型與告警代碼需相符）？輸出 {"relevant": true 或 false}')
        if not rel["relevant"]:
            continue
        # ③ 只根據這一段寫一句草稿
        draft = client.messages.create(model=MODEL, max_tokens=200,
            messages=[{"role": "user", "content":
                f'只根據下列段落，用一兩句回答問題。段落沒寫的不要補。\n問題：{question}\n段落：{p["text"]}'}]
        ).content[0].text
        # ④ [IsSup]：草稿是否被段落完全支持？
        sup = ask_json(f'段落：{p["text"]}\n草稿：{draft}\n'
                       '草稿的每個主張是否都能在段落找到依據？輸出 {"support": "full" 或 "partial" 或 "none"}')
        if sup["support"] == "full":   # 想更完整可放寬成 full / partial
            kept.append({"source": p["id"], "text": draft})

    # ⑤ 沒有任何有依據的草稿：明講查無依據，不硬編
    if not kept:
        return "手冊與工單中查無足夠依據，建議改查對應章節或詢問原廠。"
    return "\n".join(f'{k["text"]}（來源：{k["source"]}）' for k in kept)

print(self_rag("PT-203 旋角馬達過溫怎麼處理"))
print(self_rag("旋角系統是做什麼用的"))

這個近似做法每個段落最多多 3 次 LLM 呼叫（相關性、草稿、支持度），延遲與費用比原論文把批判內建在單一模型裡高；實務上可以把前兩步合併，或只對重要問題啟用。

Self-RAG 處理的是「流程由誰控制」，和前面的檢索技巧可以疊加：檢索端用混合檢索加重排序，生成端再用 Self-RAG 風格的自我檢查。下一類方法（CRAG、Adaptive RAG）也是在檢索結果不好時換路線，差別在判斷由外部評估器而非單一模型負責。

⚠️ Self-RAG 常見的坑 / 何時不該用

  • 批判模型也會錯：[IsRel] 把舊款 OW-6 段落判成相關，或 [IsSup] 把「過度推論」判成有支持，都會讓壞內容溜進答案。要用評估集量測批判的精確率與召回率。
  • 支持度太嚴會漏答：互動範例把要求調成「僅完全支持」，帶有個案推論的句子被丟掉，答案變短。查手冊這類高風險場景偏向嚴謹，但要接受「寧缺勿濫」。
  • [Retrieve] = No 可能放過該查的題：模型自信地用記憶回答「保養週期」，數字可能過時或根本是編的。涉及告警代碼、料號、門檻值的題目，建議用規則強制檢索。
  • 「有支持」不等於「正確」：段落本身可能過期或是舊版手冊，IsSup 只檢查句子與段落一致。版本與機型仍要靠中繼資料過濾（第 011 堂）。
  • 訓練與維護成本高：原始做法要建批判資料、微調模型；換領域或換基底模型就得重來。資源有限時，先從提示詞式評審加評估集開始。
  • 延遲與費用：逐段評審會讓呼叫次數成倍增加。簡單問答、延遲敏感的場景，固定流程的 RAG 加重排序通常更划算。
風場、機型、手冊內容與數據皆為虛構，實際作業以原廠手冊與現場規範為準。互動範例的檢索為簡化的 TF-IDF 模擬，[Retrieve] 與 [IsRel] 以人工標註模擬；範例中的告警代碼、步驟與門檻僅供教學示範。

延伸閱讀：Asai、Wu、Wang、Sil、Hajishirzi，〈Self-RAG: Learning to Retrieve, Generate, and Critique through Self-Reflection〉（arXiv:2310.11511，ICLR 2024）。

📝 小測驗

Self-RAG 的 [IsSup] 反思詞元在檢查什麼？

A 是 [IsRel]，C 是 [Retrieve]。[IsSup] 檢查生成內容被段落支持的程度（完全、部分、無），用來抓出模型在段落之外自行補上的主張。

技師問「PT-203 怎麼處理」，檢索到舊款 OW-6 的過溫段落（代碼 PT-103）。Self-RAG 最可能怎麼處理它？

[IsRel] 逐段判斷段落能否用來回答問題，機型或告警代碼對不上就判為無關。但批判模型可能判斷錯誤，所以仍需要機型過濾與評估集把關。
